# 奇美拉误报归因与改进闭环

## 我们的情况

- 误报率降不下来，目标是降误报。
- 人工终审只给「是不是漏洞」和一个很粗的原因。
- 测评平台能分析 trace、给根因，但后面没有闭环。
- 路径是自进化：扫描平台能从 trace 自己诊断、自己改、自己验证。

## 想做的闭环

```
漏洞扫描 → 人工确认 → 测评分析 trace → 根因假设 H1..Hn → 按假设 replay → 验证
                                       ↑                           │
                                       └─ 未解决：排除该假设，试下一个 ←┘
```

一句话：根因可能不止一个，要逐个假设 replay 验证，直到找到真实根因或全部排除。

## 漏洞是怎么产生的

- **挖掘 Agent**：入口识别 → 数据流追踪 → 模式识别 → Sink → 上报
- **验证 Agent**：理解 → 定位 → 验证 → 确认/否定
- **知识/记忆系统**：按需访问，提供模式、经验、文档

根因可能在这三者之一，也可能都不是——模型幻觉、评测匹配、环境问题。不预设责任方。

## 现状

**已经有的**
- 人工确认：给出「是不是漏洞」，原因从固定下拉里选一项：
  - 模型幻觉
  - 重复上报
  - 判断错误
  - 测试/示例代码
  - 输入实际可控或已过滤校验
  - 上下文不足导致
  - 业务场景需要
  - 有框架防御但未提供
  - 其他误报原因
  - 其他非平台工具原因
- 测评分析：能逐 case 分析 trace、反推根因，可能给出多个假设。
- 问题单与看板：根因能落成问题单，按 Agent / 成因统计。
- 自进化：方向已经定了，诊断这一段有了。

**还没做的**
- replay：测评平台还不能发起重放。
- 独立验证：还不能基于 replay 日志判断是否真的解决。
- 迭代：还不能排除一个假设、试下一个。
- 自进化闭环：诊断 → 适配 → 验证 → 沉淀，还没走通。

一句话：**前半段（确认、分析、提单）已经有了；后半段（replay、验证、迭代、自进化）还没接上。**

## 目标：降误报；路径：自进化

让扫描平台能从 trace 自己诊断、自己改、自己验证。

对应三件事，也是可以一起聊的部分：

1. **诊断：从 trace 找出该改什么**
   你的失效诊断（尤其是“结果对 ≠ 推理对”，以及多 LLM 候选原因 + 人工编码 + 知识充分性判定）正好补我们“只有 FP 标签、没有原因”的缺口。
2. **适配：把诊断变成具体改动**
   你强调不改模型参数、只做 harness/agent 侧适配；我们也在看知识、提示词、流程这几层该怎么改。
3. **验证：证明真的进化了**
   你用未见任务验证，正好点出我们的短板：只重放原 case，只能证明这个 case 修好了，不能证明没有过拟合。

你不需要解决奇美拉内部的 replay 执行、多 Agent 挖掘/验证改造、人工终审——这些我们自己来。你的实验对象是小模型渗透测试，我们是多 Agent 挖掘 + 验证，方法论可迁移，结论不完全通用。

## 需要交流的问题

1. 多个 LLM 生成候选原因 + 人工编码，在只有 FP 标签、没有人工原因的场景下，怎么保证一致性？
2. 从诊断到具体改动，怎么判断该改知识、提示词还是 harness？改多少算够？
3. 只重放原 case 怎么判断不是过拟合？什么时候必须上未见任务？

也想听听：做过什么、能提供什么形态、需要我们给什么、看到什么风险。

可以先给脱敏的单 case + trace 看看。
