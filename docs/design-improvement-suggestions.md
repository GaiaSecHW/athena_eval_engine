# 知识与记忆接入对漏洞挖掘/验证误报率消减 测评方案设计

## 1. 背景与目标

### 1.1 背景

漏洞挖掘流程中，4 个漏洞挖掘 Agent 和 2 个漏洞验证 Agent 接入了知识库和记忆模块（记忆模块中包含知识升维的进化模块）。需要测评这些知识/记忆的接入对误报率和漏报率的影响，并给出各 Agent 的改进方向。

### 1.2 两阶段目标

| 阶段 | 核心指标 | 说明 |
|------|----------|------|
| 第一阶段 | 误报率消减 | 重点关注接入知识/记忆后，误报率是否下降、哪些环节导致误报 |
| 第二阶段 | 漏报率消减 | 在误报率消减的基础上，进一步关注漏报率 |

### 1.3 核心问题

知识（知识库 + 记忆模块均包含知识）在漏洞挖掘/验证流程中是否被正确召回、是否产生效果、效果是正向还是负向，以及如何归因到具体工具/模块并给出改进建议。

## 2. 分析对象

### 2.1 漏洞挖掘 Agent（4 个）

每个挖掘 Agent 的阶段：

| 阶段 | 说明 |
|------|------|
| 代码扫描与理解 | 使用 read/grep/glob 等工具扫描代码，定位漏洞 sink 点 |
| 知识/记忆召回 | 查询知识库或读取记忆，获取漏洞模式、修复建议等 |
| 漏洞判定与上报 | 判断是否为漏洞并提交 finding |

**横切度量（适用于所有阶段）**：

| 度量 | 说明 |
|------|------|
| 资源效率 | Token 消耗、步数、耗时。非工作流阶段，而是对所有阶段的横切度量 |

### 2.2 漏洞验证 Agent（2 个）

每个验证 Agent 的阶段：

| 阶段 | 说明 |
|------|------|
| 漏洞理解 | 读取 finding 描述、理解待验证漏洞、定位相关代码 |
| 知识/记忆召回 | 查询知识库或读取记忆，获取验证线索 |
| 验证执行 | 执行分析、构造 PoC、运行测试 |
| 判定上报 | 写入 verdict（confirmed / ruled_out） |

**横切度量（适用于所有阶段）**：

| 度量 | 说明 |
|------|------|
| 资源效率 | Token 消耗、步数、耗时。非工作流阶段，而是对所有阶段的横切度量 |

### 2.3 知识来源（三个独立系统）

| 系统 | 说明 |
|------|------|
| 知识库 | 漏洞模式、修复建议、sink 点特征等结构化知识 |
| 记忆模块 | 历史经验存取，提供历史挖掘/验证的经验数据 |
| 进化模块 | 知识升维进化——从历史挖掘中提炼并进化知识，产出新的结构化知识。独立于知识库和记忆模块，作为独立责任主体分析 |

**关键约束**：知识库、记忆模块、进化模块是三个独立后端系统，必须分开分析。进化模块产出的知识与知识库原始知识、记忆模块历史经验在 L4（知识存在）和 L7（影响推理）中需独立统计。

**前置条件**：三系统独立统计的前提是 Agent Trace 中能区分知识访问的目标系统。当前 Agent 调用知识库用 `athena ask` 命令，调用记忆用 `mem recall` 命令——评测引擎 parser 可通过命令模式识别。但进化模块的调用接口尚未定义，评测引擎无法识别进化模块访问。**进化模块团队需先定义调用接口和返回格式**，各 Agent 按此接口实现进化模块调用后，评测引擎 parser 才能做识别和独立统计。在此之前，进化模块相关指标无法计算，L4/L7 中进化模块部分暂时为空。

**过渡方案**：进化模块接口定义完成前，按以下规则处理：

| 维度 | 过渡期处理 | 接口定义后处理 |
|------|-----------|---------------|
| L2-L4 统计 | 仅统计知识库 + 记忆两系统，分母不含进化 | 三系统独立统计，分母含全部 |
| L7 分析 | 进化知识无法识别，如 Agent 实际调用了进化模块但 Trace 中不可区分，该部分计入"未识别来源" | 三系统独立分析 |
| 指标 M18 知识存在率 | 分母 = 知识库查询数 + 记忆查询数（不含进化） | 分母 = 三系统查询总数 |
| 指标 M22-M25 | 同上，分母不含进化 | 分母含全部 |
| 报告标注 | 报告中标注"进化模块未接入，指标分母仅含知识库+记忆" | 无需标注 |

过渡期不阻塞知识库和记忆模块的分析——两系统的 L1-L6 完整执行，L7 按对应模式（开发态 replay / 运行态证据链分析）完整执行。进化模块接口定义完成后，评测引擎 parser 新增进化检测逻辑（§14.1.1），历史数据需重跑以补充进化统计。

## 3. 知识/记忆全生命周期下钻分析

这是本方案的核心。知识/记忆从"是否需要"到"是否影响推理"经历 7 级生命周期，每一级都有明确的责任主体、分析方法和判定逻辑。误报/漏报案例可逐级下钻定位到具体生命周期环节，针对性输出各阶段责任主体的改进建议。

### 3.1 知识/记忆全生命周期（7 级下钻）

```
L1: 是否需要知识/记忆     →    L2: 发起知识/记忆访问    →    L3: 知识/记忆查询
(场景是否需要知识支撑)        (工具是否主动发起访问)          (查询是否准确)
                                                                      ↓
L7: 知识/记忆影响推理     ←    L6: 知识/记忆使用         ←    L4: 知识/记忆存在     ←    L5: 知识/记忆召回
(是否改变推理结论)              (是否被推理过程引用)              (知识库/记忆中是否有)      (是否成功取回)
```

每一级是下一级的前置条件：L1 不需要 → L2-L7 不发生；L2 未发起 → L3-L7 不发生；以此类推。这种逐级下钻的设计确保能精确定位"断链"发生在哪一级。

### 3.2 各级详细定义

责任主体和典型断链原因见§3.3 责任主体矩阵，指标定义见§6.2。以下聚焦各级的分析方法和判定逻辑。

#### L1：是否需要知识/记忆

L1 判定不依赖知识库覆盖度（覆盖度是 L4 的事），而是基于**历史误判率推断**——如果某类 case 在无知识条件下的误判率显著高于有知识条件，则判定为"需要知识"：

| 判定方法 | 说明 |
|----------|------|
| 历史误判率对比 | 对同一 vulnerability_type 的 case，对比 KG 条件和 NOGK 条件下的误判率。如果 NOGK 误判率显著高于 KG（如差值 > 10pp），则该类 case 需要知识 |
| 漏洞类型复杂度分级 | 按漏洞类型复杂度分级：高复杂度（反序列化、SSRF、跨文件数据流）→ 默认需要知识；低复杂度（简单语法级、工具规则覆盖）→ 默认不需要 |
| 基线标注 | 基线 case 集中标注 `requires_knowledge` 字段（人工或自动），作为 ground truth |

| 判定 | 条件 | 下钻方向 |
|------|------|----------|
| 需要知识 | 历史数据显示该类 case 无知识时误判率显著高，或漏洞类型属于高复杂度 | → L2 |
| 不需要知识 | 历史数据显示该类 case 无知识时误判率也低，或漏洞类型属于低复杂度 | 终止，误报与知识无关 |
| 数据不足 | 历史数据样本不足（<10 个同类型 case），无法判定 | 标注 `undetermined`，不纳入 L1 统计 |

#### L2：发起知识/记忆访问

扫描 Agent Trace 中的知识/记忆访问事件（wiki 查询、skill 调用、memory read 等），统计 L1 判定为"需要知识"的 case 中工具是否发起了访问。需要知识但未发起 → 召回意识不足。

| 判定 | 条件 | 下钻方向 |
|------|------|----------|
| 已发起访问 | L1 需要知识，且 Trace 中有知识/记忆访问事件 | → L3 |
| 未发起访问 | L1 需要知识，但 Trace 中无知识/记忆访问事件 | 断链：工具召回意识不足 |

#### L3：知识/记忆查询

提取 Agent Trace 中的知识查询内容（query 文本），对比查询内容与基线漏洞信息（source_file、vulnerability_type、sink 点），LLM 判断查询是否与当前 case 相关。

| 判定 | 条件 | 下钻方向 |
|------|------|----------|
| 查询准确 | 查询内容与当前漏洞场景匹配 | → L4 |
| 查询模糊 | 查询过于宽泛，未聚焦当前漏洞 | 断链：查询质量不足 |
| 查询错误 | 查询内容与当前漏洞无关 | 断链：查询方向错误 |

#### L4：知识/记忆存在

提取知识召回的返回内容（response 文本），分别判断知识库、记忆模块、进化模块（三个独立系统）。返回了知识 → 继续下钻；未返回 → 知识缺失。

| 判定 | 条件 | 下钻方向 |
|------|------|----------|
| 知识存在 | 返回了非空内容 | → L5 |
| 知识缺失 | 返回空或无相关内容 | 断链：知识库/记忆/进化覆盖度不足 |

#### L5：知识/记忆召回

确认工具的访问请求是否成功获取了返回内容。与 L4 的区别：L4 判断"知识是否存在"（知识库侧），L5 判断"工具是否成功取回"（工具侧 + 传输链路）。关注传输失败、解析错误、格式不兼容等工程问题。

| 判定 | 条件 | 下钻方向 |
|------|------|----------|
| 成功召回 | 工具获取并解析了返回内容 | → L6 |
| 召回失败 | 传输失败/解析错误/格式不兼容 | 断链：工程链路问题 |

#### L6：知识/记忆使用

分析知识召回之后的 Agent 推理文本（thinking/reasoning 事件），检查推理文本中是否引用了召回的知识内容。推理引用了知识 → 继续下钻判断影响；推理未引用 → "召回了但没用上"的死知识。

| 判定 | 条件 | 下钻方向 |
|------|------|----------|
| 已使用 | 推理文本中引用了召回的知识内容 | → L7 |
| 死知识 | 召回了知识但推理未引用 | 断链：工具未利用召回的知识 |

#### L7：知识/记忆影响推理

被使用的知识是否改变了工具的推理结论。通过 A/B 消融测试验证（开发态）或证据链分析（运行态）。详见 §4 和 §9.3。

| 判定 | 条件 | 下钻方向 |
|------|------|----------|
| 影响推理 | 消融测试显示行为差异（JSD > 阈值 或 Flip=True 或 语义差异=True） | → §5 端到端效果判定 |
| 未影响推理 | 消融测试显示行为一致且无语义差异 | 中性知识：知识未产生影响 |

### 3.3 责任主体矩阵

| 生命周期级别 | 责任主体 | 典型断链原因 |
|-------------|----------|-------------|
| L1 是否需要 | 人工 + 评测引擎 | 基线标注不准、知识需求判断错误 |
| L2 发起访问 | 挖掘 Agent / 验证 Agent | 召回意识不足、未识别自身知识缺口 |
| L3 查询 | 挖掘 Agent / 验证 Agent | 查询模糊、查询方向错误、未结合代码上下文 |
| L4 知识存在 | 知识库 / 记忆模块 / 进化模块 | 知识缺失、覆盖度不足、漏洞类型未收录；进化模块未产出有效知识 |
| L5 成功召回 | 挖掘 Agent / 验证 Agent + 知识库/记忆/进化 | 传输失败、解析错误、格式不兼容 |
| L6 知识使用 | 挖掘 Agent / 验证 Agent | 召回了但推理未引用、死知识 |
| L7 影响推理 | 挖掘 Agent / 验证 Agent + 评测引擎 | 知识使用了但未改变结论、知识方向错误；进化知识误导 |

## 4. 阶段性基于 Replay 的消融测试

### 4.1 设计目标

L7（知识/记忆影响推理）需要验证知识是否真正改变了工具的行为。仅靠 Trace 观察无法区分"知识被使用"和"知识实际影响了结论"——需要通过消融测试（A/B 对照）来验证。

**核心目标**：排除两类无效知识：
1. **死知识**（L6 已识别）：召回了但推理未引用
2. **无效知识**（L7 识别）：推理引用了但未改变结论

### 4.2 消融测试方法

#### 4.2.1 核心问题：LLM 推理的随机性

LLM 的推理具有随机性——同一输入跑两次，工具调用序列和推理文本可能不同。因此 A/B 分支的行为差异可能来自两个混淆因素：

1. **知识的影响**（我们要测量的信号）
2. **LLM 本身的方差**（噪声）

不消除噪声就无法归因信号。方案采用**多轮重放 + 方差基线**设计。

#### 4.2.2 方差基线建立

在 A/B 消融测试之前，先对 A 分支做 **N 轮重复重放**（同一快照、同一知识返回内容、多次重放），建立 LLM 方差基线：

| 步骤 | 说明 |
|------|------|
| A 分支 N 轮重放 | 同一快照点、保留知识返回内容，重放 N 次（N≥3） |
| 计算基线方差 | 对 N 轮 A 分支行为轨迹两两计算 JSD，取均值作为 `JSD_baseline`（LLM 本身的行为方差） |
| 判定阈值设定 | `JSD_threshold = JSD_baseline × k`（k 为灵敏度系数，默认 k=2，即 B 分支差异需超出基线方差 2 倍才算"知识影响"） |

**关键约束**：如果 `JSD_baseline` 本身很高（LLM 方差大），说明该 case 的行为对随机性敏感，消融测试结论不可靠——标记为 `unstable`，不纳入 L7 统计。

#### 4.2.3 快照点

快照点不是"知识召回时刻"，而是**知识返回后的下一个推理步开始前**——此时知识返回内容已就绪，Agent 即将基于知识做下一步推理。

| 快照内容 | 说明 |
|----------|------|
| 代码上下文 | 已读取的文件内容、当前分析的代码位置 |
| 工具调用历史 | 此前的工具调用序列及返回结果 |
| Agent 状态 | 推理上下文、已形成的初步判断 |
| 知识返回内容 | 原始知识/记忆返回的完整内容 |
| 知识返回来源 | 标记知识来自知识库/记忆/进化（三系统独立） |

**关键约束**：快照必须在知识返回内容完整传入推理上下文之后、下一步推理开始之前。如果 Agent 的知识召回和推理在同一步内完成（不可分割），则该 case 不适合做 replay，标记为 `non_replayable`。

#### 4.2.4 A/B 分支重放

| 分支 | 条件 | 说明 |
|------|------|------|
| A 分支（加入知识） | 保留原始知识返回内容 | 重现真实行为轨迹。A 分支不重放——直接使用原始 Trace 中快照点之后的真实行为轨迹作为 A 分支结果 |
| B 分支（关闭知识） | 将知识返回内容置空 | 从快照点出发，重放后续推理和工具调用 |
| B 分支多轮重放 | B 分支重放 N 次（N≥3） | 建立 B 分支的方差估计，与 A 分支（原始 Trace，单次）比较时考虑 B 分支方差 |

**A 分支用原始 Trace 而非重放的原因**：A 分支重放的结果不会比原始 Trace 更真实——原始 Trace 就是 Agent 在真实环境中的实际行为。重放 A 分支只增加 LLM 方差，不增加信息量。B 分支必须重放因为我们需要"如果没有知识"的反事实场景。

#### 4.2.5 行为差异指标（三层指标）

**指标 1：工具调用序列差异（JSD）**

- 对 A（原始 Trace）和 B（重放）两条行为轨迹的工具调用分布计算 Jensen-Shannon Divergence
- JSD > `JSD_threshold`（超出基线方差 k 倍） → 行为发生了变化
- JSD ≤ `JSD_threshold` → 行为差异在 LLM 方差范围内，不构成信号

**指标 2：判定翻转（Flip）**

- 比较 A（原始 Trace 最终判定）和 B（重放最终判定）
- A 判定 confirmed，B 判定 ruled_out → 判定翻转（Flip=True）
- A 和 B 判定一致 → 判定未翻转（Flip=False）
- B 分支多轮重放中判定不一致 → 说明判定对 LLM 随机性敏感，标记 `judgment_unstable`

**指标 3：推理语义差异（LLM 辅助判断）**

- JSD 和 Flip 都无法捕捉"工具调用相同但推理逻辑不同"的情况
- 当 JSD ≤ 阈值 且 Flip=False 时，用 LLM 对 A/B 两条推理文本做语义对比：
  - A 的推理是否引用了知识内容并据此做判断？
  - B 的推理在无知识情况下是否用了不同的推理路径？
  - LLM 输出 `semantic_diff` (bool) + `reason`

**综合判定逻辑**：

| JSD | Flip | 语义差异 | 判定 | 含义 |
|-----|------|----------|------|------|
| > 阈值 | True | - | 知识影响推理 | 知识改变了行为且翻转了判定 → 强影响 |
| > 阈值 | False | - | 知识影响推理 | 知识改变了行为但未翻转判定 → 中等影响 |
| ≤ 阈值 | True | - | 知识影响推理 | 行为分布一致但判定翻转 → 知识影响了判定逻辑而非工具选择 |
| ≤ 阈值 | False | True | 知识影响推理 | 工具和判定一致但推理路径不同 → 弱影响 |
| ≤ 阈值 | False | False | 知识未影响推理 | 行为、判定、推理均未变化 → 中性知识（死知识/无效知识） |
| unstable | unstable | - | 不可判定 | LLM 方差过大，消融测试结论不可靠 |

### 4.3 消融测试指标

| 指标 | 定义 | 含义 |
|------|------|------|
| 行为影响率 | (JSD > 阈值 或 Flip=True 或 语义差异=True) 的召回数 / 可判定召回数 | 知识实际产生效果的比例 |
| 判定翻转率 | Flip=True 的召回数 / 可判定召回数 | 知识直接改变判定的比例 |
| 平均行为散度 | 所有可判定召回的 JSD 均值 | 知识对行为的整体影响程度 |
| 死知识率 | (L6 未使用 + L7 未影响) 的召回数 / 总召回数 | 无效知识的总比例 |
| 强影响率 | JSD > 阈值 且 Flip=True 的召回数 / 可判定召回数 | 知识同时改变行为和判定的比例 |
| 消融不可判定率 | unstable 或 non_replayable 的召回数 / 总召回数 | LLM 方差过大或快照不可分割的比例 |
| 知识来源影响率 | 按知识库/记忆/进化分别计算行为影响率 | 三系统各自的效果（独立） |

### 4.4 Replay 实现要求

消融测试需要工具/验证 Agent 具备 Trace 重放功能：

| 要求 | 说明 | 责任方 |
|------|------|--------|
| 快照能力 | 在知识返回后的下一个推理步开始前保存完整上下文（含知识返回内容和来源标记） | 各工具/验证 Agent 实现 |
| 快照可分割性 | 知识召回和后续推理必须可在 Trace 中分割（快照点存在）。如不可分割则标记 `non_replayable` | 各工具/验证 Agent 实现 |
| A 分支 | 不重放——直接使用原始 Trace 中快照点之后的真实行为轨迹 | 评测引擎提取 |
| B 分支重放 | 置空知识返回内容，从快照点重放后续推理 | 各工具/验证 Agent 实现 |
| B 分支多轮重放 | B 分支重放 N 次（N≥3），建立 B 分支方差估计 | 各工具/验证 Agent 实现 |
| 方差基线 | A 分支 N 轮重放建立 `JSD_baseline`（可选，如 Agent 支持同输入多次重放） | 各工具/验证 Agent 实现 |
| 行为采集 | 采集 A/B 分支的工具调用序列、推理文本、判定结果 | 各工具/验证 Agent 实现 |
| JSD 计算 | 对 A/B 行为分布计算散度，与 `JSD_threshold` 比较 | 评测引擎计算 |
| Flip 判定 | 比较 A/B 最终判定，B 分支多轮判定不一致时标记 `judgment_unstable` | 评测引擎计算 |
| 语义差异判断 | JSD ≤ 阈值 且 Flip=False 时 LLM 辅助判断推理语义差异 | 评测引擎计算 |

**评测引擎定义 replay 协议**（快照点位置、快照格式、A/B 分支规范、行为采集格式、多轮重放协议），各团队按协议实现 replay 功能并返回结果。

**Replay 成本控制**：每个知识召回点需要 1 次 A 分支（原始 Trace，零成本）+ N 次 B 分支重放（N≥3）。一个 case 可能有多个知识召回点，总重放次数 = 召回点数 × N。对于召回点过多的 case（如 >10 个），按时间顺序取前 5 个和最后 2 个做 replay（采样），标记 `sampled_replay`。

## 5. 端到端效果判定

### 5.1 判定方法

L7 判定为"知识影响推理"的案例，进一步判定影响方向：

1. **端到端结果标注**：人工标注经过挖掘和验证 Agent 之后产出的报告中每个 finding 是误报（FP）还是正报（TP）。该报告属于端到端结果。
2. **Agent Trace 溯源**：对每个端到端结果（FP/TP），溯源到对应的 Agent Trace，定位 Trace 中该 case 的知识召回事件。
3. **影响方向判定**：结合 L7 消融测试结果：

| 端到端结果 | 消融测试 | 判定 | 含义 |
|------------|----------|------|------|
| 正报（TP） | A 正报，B 误报/漏报 | 正向效果知识 | 知识促成正确判定 |
| 误报（FP） | A 误报，B 正报/正确排除 | 负向效果知识 | 知识误导导致误报 |
| 正报（TP） | A 正报，B 也正报 | 中性知识 | 知识未影响结论（判定一致） |
| 误报（FP） | A 误报，B 也误报 | 中性知识 | 知识未影响结论（判定一致） |

### 5.2 端到端效果指标

| 指标 | 定义 | 含义 |
|------|------|------|
| 正向知识率 | 正向效果知识数 / 有行为变化的知识数 | 知识产生帮助的比例 |
| 负向知识率 | 负向效果知识数 / 有行为变化的知识数 | 知识产生误导的比例 |
| 中性知识率 | 行为未变化的知识数 / 总召回数 | 知识未产生影响的比例 |
| 知识净效果 | 正向知识率 - 负向知识率 | 知识接入的整体效果 |

3. **统计并呈现**：每个 Agent 呈现自身系统架构中的过程指标

## 7. 归因分析

### 7.1 归因流程

```
端到端测评结果（人工标注 FP/TP）
        ↓
    误报率升高？（举例）
        ↓
    溯源到 Agent Trace
        ↓
    知识/记忆/进化全生命周期下钻（7 级）
    定位断链发生在哪一级
        ↓
    确定责任主体（挖掘 Agent / 验证 Agent / 知识库 / 记忆 / 进化 / 人工）
        ↓
    误报因果链分层分解（§7.3）
    定位误报产生在哪个业务流程阶段
        ↓
    交叉归因：业务流程阶段 × 生命周期级别 × 责任主体
        ↓
    查看各 Agent 细粒度过程指标
        ↓
    基于工具架构和原理进行深入归因
        ↓
    归因到具体工具/模块
        ↓
    该工具/模块/阶段承担多少误报指标？
        ↓
    给出改进方向和建议（结合工具具体实现方法）
```

### 7.2 归因维度

| 归因维度 | 说明 | 示例 |
|----------|------|------|
| 按工具归因 | 哪个工具贡献了误报 | 挖掘 Agent A 承担 3% 误报 |
| 按生命周期级别归因 | 断链发生在哪一级 | L6 死知识导致 40% 误报 |
| 按责任主体归因 | 谁的责任 | 工具责任 80%，知识库责任 15%，记忆责任 5% |
| 按知识来源归因 | 知识库 vs 记忆 vs 进化分别贡献 | 知识库负向知识率 30%，记忆负向率 15%，进化负向率 10% |
| 按模块归因 | 工具内部哪个模块导致 | 知识查询模块、推理模块、判定模块 |
| 按业务流程阶段归因 | 误报产生在漏洞挖掘验证流程的哪个阶段 | 入口识别阶段贡献 5%，漏洞模式识别阶段贡献 8%（详见 §7.3） |

### 7.3 误报因果链分层分解

知识/记忆全生命周期下钻（L1-L7）定位的是"知识在哪一级断链"，但一个误报的产生不仅与知识相关——还与漏洞挖掘验证的**业务流程阶段**相关。同一个 L7 负向知识，可能发生在入口识别阶段（错误识别了数据入口），也可能发生在漏洞模式识别阶段（知识误导了漏洞判定）。需要将误报率按业务流程阶段分层拆解，实现可分层量化的阶段指标。

#### 7.3.1 漏洞挖掘验证业务流程阶段

基于平台上漏洞挖掘验证的全流程，拆解为以下因果链阶段：

**挖掘 Agent 业务流程**：

| 阶段 | 阶段 key | 说明 | 典型误报原因 |
|------|----------|------|-------------|
| 入口识别 | `entry_identification` | 识别用户可控输入源（source 点） | 将不可控输入误判为可控，导致后续分析全链路错误 |
| 数据流追踪 | `dataflow_tracking` | 追踪数据从 source 到 sink 的传播路径 | 路径断裂或追踪到不相关分支，产生虚假数据流 |
| 漏洞模式识别 | `pattern_recognition` | 判断代码模式是否符合已知漏洞模式 | 知识误导——错误模式匹配，将安全代码识别为漏洞 |
| Sink 点定位 | `sink_localization` | 定位漏洞触发的具体代码位置 | 定位到错误的 sink 点，导致对正确代码误报 |
| 漏洞判定与上报 | `judgment_reporting` | 综合判断是否为漏洞并提交 finding | 判定阈值过低，缺乏充分证据即上报 |

**验证 Agent 业务流程**：

| 阶段 | 阶段 key | 说明 | 典型误报原因 |
|------|----------|------|-------------|
| 漏洞理解 | `vuln_understanding` | 读取 finding 描述、理解待验证漏洞 | 误解 finding 含义，验证方向偏差 |
| 代码定位 | `code_localization` | 定位 finding 涉及的代码位置 | 定位到错误代码位置，验证了无关代码 |
| 验证执行 | `verification_execution` | 执行分析、构造 PoC、运行测试 | PoC 构造错误或测试不充分，错误确认漏洞 |
| 判定上报 | `judgment_reporting` | 写入 verdict（confirmed / ruled_out） | 将非漏洞判定为 confirmed（验证误报） |

#### 7.3.2 因果链断点分层统计

对每个误报 case，沿因果链逐阶段分析，定位误报产生的**断点阶段**：

```
误报 case
    ↓
入口识别正确？ — 否 → 断点: entry_identification（入口识别错误）
    ↓ 是
数据流追踪正确？ — 否 → 断点: dataflow_tracking（数据流追踪错误）
    ↓ 是
漏洞模式识别正确？ — 否 → 断点: pattern_recognition（模式识别错误）
    ↓ 是
Sink 点定位正确？ — 否 → 断点: sink_localization（Sink 定位错误）
    ↓ 是
判定与上报正确？ — 否 → 断点: judgment_reporting（判定逻辑错误）
    ↓ 是
    → 非工具流程问题，归因到知识/记忆本身（L7 负向知识）
```

每个误报 case 定位到**一个主要断点阶段**（首个出错的阶段），统计各阶段的误报承担量。

**断点定位方法**：

因果链断点定位**不靠评测引擎事后用 LLM 猜测**——Agent Trace 记录的是工具调用序列（read/grep/bash），不是结构化的"入口识别→数据流追踪→模式识别"流程。LLM 看着一堆工具调用无法可靠判断断在哪一步。

断点定位需要 **Agent 在 Trace 中主动标注业务流程阶段**（phase 标签）：

| 要求 | 说明 | 责任方 |
|------|------|--------|
| Trace 中标注 phase 标签 | Agent 在每个推理步的开始处写入当前所处的业务流程阶段（`entry_identification` / `dataflow_tracking` / `pattern_recognition` / `sink_localization` / `judgment_reporting`） | 挖掘 Agent / 验证 Agent |
| 验证 Agent phase 标签 | 验证 Agent 标注自身阶段（`vuln_understanding` / `code_localization` / `verification_execution` / `judgment_reporting`） | 验证 Agent |
| 评测引擎读取 phase 标签 | 评测引擎 parser 从 Trace 中提取 phase 标签，建立"phase → 工具调用序列 → 推理文本 → 判定"的映射 | 评测引擎 |
| 断点定位 | 评测引擎按因果链顺序检查每个 phase 的输出是否正确（与基线对比），首个输出错误的 phase 即为断点 | 评测引擎 |

**Agent phase 标注格式**：

Agent 在 Trace 的推理事件（REASONING 类型）中增加 `phase` 字段：

```json
{
  "event_type": "REASONING",
  "phase": "pattern_recognition",
  "reasoning_text": "当前代码模式匹配 SSRF 漏洞特征...",
  "timestamp": "..."
}
```

**降级方案**：如果 Agent 未实现 phase 标注，评测引擎用工具调用序列做**粗粒度推断**——按工具调用类型映射到可能的 phase（如 read+grep → 入口识别/代码定位，athena ask → 知识召回，finding 提交 → 判定上报），但标注为 `inferred`（推断），置信度低于 Agent 主动标注。

#### 7.3.3 分层量化指标

将误报率拆解成可分层量化的阶段指标：

| 指标 | 定义 | 含义 |
|------|------|------|
| 阶段误报承担率 | 该阶段断点 case 数 / 总误报 case 数 | 该阶段对误报的贡献比例 |
| 阶段误报率 | 该阶段断点 case 数 / 总 case 数 | 该阶段的绝对误报率 |
| 知识相关阶段误报率 | 知识导致断点的 case 数 / 总误报 case 数 | 误报中知识/记忆导致的比例 |
| 阶段 × 生命周期交叉 | 该阶段断点 × 该级别断链的 case 数 | 交叉定位：业务阶段 + 知识生命周期 |

#### 7.3.4 因果链与生命周期的交叉归因

因果链分层与 7 级生命周期是两个正交的归因维度，交叉分析可精确定位问题：

| 业务流程断点 | 知识生命周期断链 | 交叉含义 | 改进方向 |
|-------------|-----------------|---------|---------|
| 入口识别错误 | L3 查询模糊 | 知识查询未聚焦入口识别方法 | 改进查询：结合代码上下文查询入口识别模式 |
| 数据流追踪错误 | L6 死知识 | 召回了数据流知识但推理未引用 | 改进推理：将数据流知识注入追踪决策 |
| 漏洞模式识别错误 | L7 负向知识 | 知识误导了模式匹配（如错误模式匹配） | 改进知识：修正知识库中错误的漏洞模式 |
| 漏洞模式识别错误 | L4 知识缺失 | 该漏洞模式在知识库中不存在 | 改进知识库：补充该漏洞模式知识 |
| 验证执行错误 | L7 负向知识 | 验证知识误导了 PoC 构造 | 改进知识：修正验证线索知识 |
| 判定上报错误 | L2 召回意识缺失 | 判定阶段未查询知识，仅凭经验 | 改进工具：判定阶段增加知识触发点 |

**交叉归因场景示例**：

端到端误报率 35%，按因果链分层统计：
- 入口识别阶段断点：5%（其中 L3 查询模糊 3%，L7 负向知识 2%）
- 数据流追踪阶段断点：8%（其中 L6 死知识 5%，L4 知识缺失 3%）
- 漏洞模式识别阶段断点：15%（其中 L7 负向知识 10%，L4 知识缺失 5%）
- Sink 点定位阶段断点：3%（其中 L2 召回意识缺失 2%，L3 查询错误 1%）
- 判定与上报阶段断点：4%（其中 L2 召回意识缺失 2%，无知识相关 2%）

→ 改进优先级：漏洞模式识别阶段 L7 负向知识（10%）> 数据流追踪阶段 L6 死知识（5%）> 漏洞模式识别阶段 L4 知识缺失（5%）

#### 7.3.5 因果链分层与开发态/运行态

| 维度 | 开发态 | 运行态 |
|------|--------|--------|
| 因果链分析数据 | 基线集 Trace（可重复分析） | 生产 Trace（离线分析） |
| 断点定位方法 | Trace 逐阶段分析 + replay 验证 | Trace 逐阶段分析（无 replay） |
| 阶段指标精度 | 高（控制变量，可重复） | 中（单次分析，无对照） |
| 知识相关断点定位 | L7 replay 精确区分正/负向 | L7 LLM 语义分析近似估计 |

## 8. 改进建议生成

### 8.1 生成方式

**规则检测 + LLM 生成**混合模式：

1. **规则检测**（确定性）：从全生命周期下钻结果中按预定义规则检测异常模式，每条规则有触发条件和结构化证据
2. **LLM 生成**（可选）：将下钻结果 + 证据喂给 LLM，生成结合工具具体实现方法的改进建议

### 8.2 改进建议结构

每条改进建议包含：

| 字段 | 说明 |
|------|------|
| 维度 | 挖掘 Agent / 验证 Agent / 知识库 / 记忆模块 |
| 工具 | 具体工具名称 |
| 生命周期级别 | 断链发生在 L1-L7 的哪一级 |
| 责任主体 | 工具 / 知识库 / 记忆 / 人工 |
| 证据摘要 | 数据支撑的发现（case 列表、指标值、断链位置） |
| 改进建议 | 结合工具具体实现方法的改进方向 |
| 预期影响 | 改进后哪个指标会改善、误报率可消减多少 |
| 优先级 | high（影响 TP/FP）/ medium（影响资源）/ low（观察性） |
| KG 对比 | KG vs NOGK 对比结论（如有对照数据） |

### 8.3 改进建议的约束

- **结合工具具体实现方法**：不能泛泛说"改进查询逻辑"，要基于工具的架构原理展开（如"将关键词匹配升级为代码上下文+漏洞类型组合查询"）
- **基于数据**：所有建议必须由全生命周期下钻的数据支撑
- **可消减量化**：预期影响要量化（如"预计消减 3% 误报率"）
- **责任主体明确**：每条建议必须明确指向责任主体（工具/知识库/记忆/人工）

### 8.4 改进建议闭环追踪

改进建议不是一次性产出——从建议生成到落实验证形成闭环：

| 阶段 | 说明 | 责任方 |
|------|------|--------|
| 建议生成 | 测评报告产出改进建议，每条建议分配唯一 `suggestion_id`，标注责任主体和预期影响 | 评测引擎 |
| 建议分发 | 按 `suggestion_id` 分发给对应责任主体（挖掘 Agent 团队 / 验证 Agent 团队 / 知识库团队 / 记忆模块团队 / 进化模块团队） | 评测引擎 → 各团队 |
| 建议落实 | 各团队按建议做改进，标注 `suggestion_id` → `resolved` / `deferred` / `rejected`（附理由） | 各团队 |
| 效果验证 | 下一版本开发态测评中对比：建议落实前后的指标变化（如负向知识率是否下降、L6 死知识率是否消减） | 评测引擎 |
| 闭环判定 | 建议落实 + 指标改善 → `closed`；建议落实但指标未改善 → `reopened`（需重新分析根因）；建议未落实 → `open` | 评测引擎 |

**版本对比**：开发态测评每次触发时，自动加载上一版本的改进建议清单，对比当前版本指标变化，更新每条建议的闭环状态。报告中新建议和未闭环建议并列展示。

**运行态反馈**：运行态测评产出的改进建议，反馈到下一版本开发态测评验证。运行态发现的问题 case 补入开发态基线集（§9.4），作为建议效果验证的测试数据。

## 9. 开发态与运行态双模式

### 9.0 当前实现状态与演进方向

当前系统基于工具 Trace 分析，已实现针对误报的端到端（E2E）评测功能。本方案在现有 E2E 评测基础上，从三个方向对知识/记忆进行细化评测：

| 演进方向 | 当前状态 | 目标状态 | 对应章节 |
|----------|---------|---------|---------|
| 知识记忆全生命周期过程指标体系 | 未实现逐级下钻 | 7 级生命周期逐级下钻，各阶段映射到挖掘工具/验证工具/知识库/记忆/进化等主体 | §3 |
| 误报因果链分层分解 | E2E 误报率（整体） | 按漏洞挖掘验证业务流程拆解因果链，断点分层统计，误报率拆解为可分层量化的阶段指标 | §7.3 |
| 基于 Replay 的消融测试 | 未实现 | 知识召回节点快照 + A/B 重放 + JSD/Flip 双指标 | §4 |

### 9.1 两种模式定义

系统支持两种测评模式，核心差异在于**触发时机**、**基线来源**和**对照组设置**：

| 维度 | 开发态测评 | 运行态测评 |
|------|-----------|-----------|
| **触发时机** | Agent 发布新版本时 | Agent 正常完成一个项目的测试后 |
| **基线来源** | 预置基线集（V-Bench / 漏洞中心已确认 case 集） | 漏洞中心人工确认结果（项目运行后产出） |
| **对照组** | KG vs NOGK（同一基线集，控制变量） | 有 KG vs 无 KG（同一项目，历史版本对比或同项目关闭 KG 重跑） |
| **数据可控性** | 高——基线集固定、可重复、可 replay | 低——依赖人工确认进度、项目数据不可重复 |
| **Replay 可行性** | 完全可行——基线集可反复执行，快照+重放无副作用 | 受限——生产 trace 无法重放（已产生副作用），只能做离线分析 |
| **测评目标** | 版本回归验证——新版本是否比旧版本好 | 生产效果评估——知识/记忆在实际项目中是否有效 |
| **时效性** | 发布前阻断——不达标不发布 | 事后评估——已完成的测试结果分析 |

### 9.2 开发态测评流程

开发态在 Agent 发布新版本时触发，使用预置基线集做控制变量实验：

```
开发态测评流程
  ├── 触发: Agent 新版本发布（CI/CD 管线）
  ├── 基线集: 预置 benchmark（V-Bench 或漏洞中心已确认 case 集）
  ├── 对照组设置
  │     ├── A 组: 新版本 + KG 开启
  │     ├── B 组: 新版本 + KG 关闭（NOGK）
  │     └── （可选）C 组: 旧版本 + KG 开启（版本回归对比）
  ├── 执行
  │     ├── 对基线集所有 case 运行 A/B/C 组
  │     ├── 采集完整 Trace（含知识召回快照点）
  │     └── 执行 Replay 消融测试（A/B 快照重放）
  ├── 分析
  │     ├── 端到端 FPR/FNR 计算（基线集已知 ground truth）
  │     ├── 知识/记忆全生命周期 7 级下钻
  │     ├── 消融测试 JSD + Flip 双指标
  │     └── 归因 + 改进建议
  └── 门禁: FPR 未消减或负向知识率超阈值 → 阻断发布
```

**开发态优势**：
- 基线集固定可重复，支持 KG vs NOGK 严格对照
- 可执行 Replay 消融测试（快照+A/B 重放）
- 版本回归对比（新版本 vs 旧版本）
- 发布前阻断不达标版本

**开发态约束**：
- 基线集覆盖度有限，可能遗漏生产场景
- Replay 需要各 Agent 团队实现快照+重放功能

### 9.3 运行态测评流程

运行态在 Agent 完成一个项目的测试后触发，使用漏洞中心人工确认结果作为基线：

```
运行态测评流程
  ├── 触发: 项目测试完成 + 漏洞中心人工确认结果就绪
  ├── 基线来源: 漏洞中心 Chimera 人工确认 case
  │     ├── 漏洞（confirmation_status=vulnerable）
  │     └── 非漏洞（confirmation_status=not_vulnerable）
  ├── 对照组设置（三种策略，按数据可用性选择）
  │     ├── 策略 1: 同项目 KG vs NOGK（需项目支持双跑）
  │     ├── 策略 2: 同项目当前版本 vs 历史版本（需历史数据）
  │     └── 策略 3: 无对照组——仅做单次分析，用基线 ground truth 评估
  ├── 分析
  │     ├── 端到端 FPR/FNR 计算（基于人工确认结果）
  │     ├── 知识/记忆全生命周期 7 级下钻（离线 Trace 分析）
  │     ├── L1-L6: 完整执行（基于 Trace 离线分析，无需 replay）
  │     ├── L7: 证据链分析（无 replay，基于 Trace 因果推理）
  │     │     ├── 提取知识召回内容 → 推理引用片段 → 判定结论的因果链
  │     │     ├── 程序化分析：知识内容是否与判定方向一致（正向/负向/中性）
  │     │     └── LLM 辅助：知识内容与漏洞基线对比，判断知识是否正确
  │     └── 归因 + 改进建议
  └── 输出: 生产效果评估报告，反馈到下一版本开发态测评
```

**运行态优势**：
- 真实生产数据，覆盖开发态基线集遗漏的场景
- 人工确认结果作为 ground truth，端到端可信
- 无需 Agent 团队额外实现 replay 功能

**运行态约束**：
- 无法做严格 KG vs NOGK 对照（除非项目支持双跑）
- L7 无 replay，用证据链分析替代——精度低于开发态的 replay（无法做反事实推理，只能做因果链分析）
- 依赖人工确认进度，有时效延迟

**运行态输出时效**：运行态测评由人工触发，触发前提是"Agent Trace + 人工确认结果 + 漏洞中心 case 数据"三者就绪。触发后评测引擎在 2 工作日内完成 L1-L6 离线分析 + L7 证据链分析 + 归因 + 报告产出。报告为一次性产出（非增量更新），因为 L1-L7 分析需要完整 case 集做统计。如人工确认分批产出，需等全部确认完成后再触发，避免分母不一致。

**运行态 L7 证据链分析方法**：

运行态无法做 replay（生产 Trace 不可重放），也不能用"LLM 模拟移除知识后推理"——LLM 已经在 Trace 中见过知识内容，无法真正模拟"不知道"的状态。这不是精度降级，而是方法论根本不可行。

替代方案是**证据链分析**——从 Trace 中提取知识对判定的因果影响链，不做反事实推理：

```
证据链分析流程
  ├── Step 1: 提取知识召回内容
  │     └── 从 Trace 中提取知识返回的完整内容（知识库/记忆/进化独立）
  ├── Step 2: 提取推理引用片段
  │     └── L6 已完成——定位推理文本中引用知识的片段
  ├── Step 3: 提取判定结论
  │     └── 从 Trace 中提取 Agent 最终判定（finding/verdict）
  ├── Step 4: 因果链分析（程序化）
  │     ├── 知识内容方向分析：知识内容是否指向"是漏洞"或"不是漏洞"
  │     ├── 判定方向分析：Agent 最终判定是"是漏洞"（confirmed/finding）还是"不是漏洞"（ruled_out）
  │     └── 方向一致性：知识方向与判定方向是否一致
  │           ├── 一致 → 知识可能影响了判定（正向或负向取决于知识是否正确）
  │           └── 不一致 → 知识未影响判定（中性知识）
  ├── Step 5: 知识正确性判断（LLM 辅助）
  │     └── LLM 对比知识内容与基线漏洞信息，判断知识是否正确
  │           ├── 知识正确 + 判定方向一致 → 正向效果知识
  │           ├── 知识错误 + 判定方向一致 → 负向效果知识（知识误导了判定）
  │           └── 判定方向不一致 → 中性知识（知识未影响判定）
  └── Step 6: 置信度标注
        ├── 高置信：知识内容明确指向某方向，推理文本直接引用，判定方向一致
        ├── 中置信：知识内容方向模糊，或推理引用间接
        └── 低置信：推理引用关系不确定，或知识内容方向不明确
```

**证据链分析 vs Replay 消融测试的精度差异**：

| 维度 | Replay（开发态） | 证据链分析（运行态） |
|------|-----------------|---------------------|
| 方法论 | 反事实推理（A/B 对照） | 因果链推理（证据链分析） |
| 能否区分"使用了但未影响" | 能（B 分支判定不变 → 中性） | 不能（只能判断方向一致性，无法排除"即使没有知识也会得出相同判定"） |
| 能否区分正向/负向 | 能（A 正报 B 误报 → 正向；A 误报 B 正报 → 负向） | 能（知识正确性 × 方向一致性 → 正向/负向） |
| LLM 随机性影响 | 有（需多轮重放消除） | 无（不做重放，只做离线分析） |
| 置信度 | 高（有对照组） | 中（无对照组，靠证据链推理） |
| 适用场景 | 开发态（可重放） | 运行态（不可重放） |

证据链分析的核心局限：无法排除"即使没有知识，Agent 也会得出相同判定"的情况。一个 case 可能知识方向与判定方向一致，但实际上 Agent 的判定是基于代码分析而非知识——知识只是"恰好方向一致"但并未真正影响。Replay 通过反事实推理可以排除这种情况，证据链分析不能。

### 9.4 两种模式的协作关系

开发态与运行态不是独立的两套系统，而是**互相补充的闭环**：

```
运行态测评（生产）
  ├── 发现生产场景中的问题（基线集未覆盖的漏洞类型、知识缺失）
  ├── 将生产 case 补入开发态基线集
  └── 产出: 新基线 case → 补入开发态基线集
                    ↓
开发态测评（发布前）
  ├── 用扩展后的基线集做严格对照实验
  ├── 执行完整 Replay 消融测试
  ├── 验证改进效果（版本回归）
  └── 产出: 改进后的 Agent 发布 → 进入生产 → 触发下一轮运行态测评
                    ↓
              （闭环）
```

| 协作机制 | 说明 |
|----------|------|
| 运行态 → 开发态 | 运行态发现的问题 case 补入开发态基线集，扩展覆盖度 |
| 开发态 → 运行态 | 开发态验证的改进版本发布后，运行态评估实际生产效果 |
| L7 精度互补 | 开发态用 replay 做反事实推理（精确）；运行态用证据链分析做因果推理（近似）。两者交叉验证：开发态基线集 case 可同时用两种方法，对比结果差异作为证据链分析的误差估计 |
| 基线集进化 | 运行态持续贡献新 case，开发态基线集持续扩展 |

### 9.5 两种模式的指标差异

同一套 7 级生命周期指标体系在两种模式下的数据来源和精度不同：

| 生命周期级别 | 开发态（基线集+replay） | 运行态（生产+人工确认） |
|-------------|----------------------|----------------------|
| L1 知识需求率 | 基于基线集漏洞类型分布 | 基于项目实际漏洞类型分布 |
| L2 访问发起率 | Trace 分析（同） | Trace 分析（同） |
| L3 查询准确率 | LLM 判断（同） | LLM 判断（同） |
| L4 知识存在率 | 知识库/记忆返回内容（同） | 知识库/记忆返回内容（同） |
| L5 召回成功率 | Trace 分析（同） | Trace 分析（同） |
| L6 知识使用率 | Trace 推理文本分析（同） | Trace 推理文本分析（同） |
| L7 行为影响率 | **Replay A/B + JSD 精确测量**（反事实推理） | **证据链分析**（因果链推理，无反事实） |
| L7 判定翻转率 | **Replay A/B + Flip 精确测量** | **方向一致性分析**（知识方向 vs 判定方向） |
| L7 正向/负向判定 | A/B 对照组直接判定 | 知识正确性 × 方向一致性推理（置信度标注） |
| E2E FPR | 基线集已知 ground truth | 漏洞中心人工确认结果 |
| KG vs NOGK | 严格对照（同基线集双跑） | 近似对照（历史版本或单次分析） |

L1-L6 在两种模式下方法论一致（都是 Trace 离线分析），差异仅在数据来源。L7 是两种模式的核心差异点：开发态用 replay 做反事实推理（精确但需 Agent 改造），运行态用证据链分析做因果推理（不需 Agent 改造但无法排除"恰好方向一致"的假阳性）。两种方法的精度差异在"中性知识"判定上最大——replay 能区分"使用了但未影响"和"影响了但方向恰好一致"，证据链分析不能。

### 9.6 模式选择规则

| 场景 | 选择模式 | 原因 |
|------|----------|------|
| Agent 新版本发布前 | 开发态 | 需要严格对照 + replay + 门禁阻断 |
| 项目测试完成后 | 运行态 | 利用人工确认结果，评估生产效果 |
| 基线集覆盖度不足 | 运行态 → 补入开发态 | 运行态发现新场景，扩展基线集 |
| 改进效果验证 | 开发态 | 版本回归对比，可重复执行 |
| 知识库/记忆模块更新 | 开发态 | 需要控制变量验证知识变更效果 |
| 生产问题排查 | 运行态 | 基于真实生产 Trace 分析 |

## 10. 跨团队协作

### 10.1 职责分工

| 责任方 | 职责 |
|--------|------|
| 评测引擎 | 定义指标体系、生命周期下钻框架、消融测试协议、归因框架、因果链分层框架、改进建议生成；执行端到端分析和归因 |
| 挖掘 Agent 团队（4 个） | 提供 Trace 数据、实现 replay 功能（快照+A/B 重放+行为采集）、提供过程指标数据 |
| 验证 Agent 团队（2 个） | 提供 Trace 数据、实现 replay 功能、提供过程指标数据 |
| 知识库团队 | 提供知识覆盖度数据、知识内容质量数据、返回内容来源标记 |
| 记忆模块团队 | 提供记忆内容数据、记忆覆盖度数据、返回内容来源标记 |
| 进化模块团队 | 定义调用接口（blocking 前置项）、提供进化知识产出数据、覆盖度与质量数据 |
| 人工标注团队 | 标注端到端结果（FP/TP/FN/TN），作为端到端基准 |

### 10.2 数据交付 SLA

两种测评模式均由人工触发，但触发后各系统的数据交付需满足以下 SLA：

| 数据 | 交付方 | 开发态 SLA | 运行态 SLA | 用途 |
|------|--------|-----------|-----------|------|
| Agent Trace（含 phase 标注、推理事件） | 挖掘/验证 Agent 团队 | 触发后 1 工作日内交付 | 触发后 1 工作日内交付 | L1-L6 分析 + 因果链 |
| Replay 结果（快照+B 分支重放+行为采集） | 挖掘/验证 Agent 团队 | 触发后 3 工作日内交付 | 不适用 | L7 开发态 |
| 人工确认结果 | 人工标注团队 | 不适用（基线集已确认） | 触发时需已就绪 | E2E FPR/FNR |
| 知识库覆盖度 + 质量数据 | 知识库团队 | 触发后 2 工作日内交付 | 触发后 2 工作日内交付 | L1/L4 归因 |
| 记忆覆盖度 + 质量数据 | 记忆模块团队 | 同上 | 同上 | L1/L4 归因 |
| 进化模块数据 | 进化模块团队 | 接口定义后按上述 SLA | 同左 | L4/L7 进化独立统计 |

**逾期处理**：数据交付逾期时，评测引擎标注该部分指标为 `DATA_PENDING`，不阻塞其他已完成数据的分析。逾期超过 5 个工作日，该批数据标记为 `DATA_EXPIRED`，需重新触发测评。

### 11.1 测评报告

| 报告段 | 内容 | 消费方 |
|--------|------|--------|
| 端到端指标报告 | E2E FPR/FNR、KG vs NOGK 对比（标注测评模式：开发态/运行态） | 评测方 |
| 全生命周期下钻报告 | 7 级分析结果、断链定位、过程指标 | 评测方 + 各团队 |
| 消融测试报告 | 开发态：A/B replay + JSD/Flip 精确结果；运行态：LLM 语义分析近似结果 | 评测方 + 各团队 |
| 归因分析报告 | 误报/漏报归因到工具/模块/生命周期级别/责任主体 | 评测方 + 各团队 |
| 改进建议报告 | 结合工具实现方法的改进方向，按责任主体分类 | 各团队 |
| 工具过程指标看板 | 各 Agent 的过程指标统计 | 各团队 |

### 11.2 输入→输出映射与降级链

每项输出依赖特定输入数据。当输入数据缺失或降级时，输出按以下映射降级：

| 输出报告 | 依赖输入 | 输入缺失时的降级 | 降级标注 |
|----------|----------|-----------------|----------|
| 端到端指标报告 | 人工确认结果（运行态）/ 基线集 ground truth（开发态） | 运行态：阻塞（不启动）；开发态：不缺失 | - |
| 全生命周期下钻报告（L1-L6） | Agent Trace（知识访问事件、返回内容、推理事件） | L6 无推理事件 → L6/L7 标注 `DATA_MISSING`，L1-L5 正常输出 | "L6+L7 不可判定" |
| 全生命周期下钻报告（L7 开发态） | Replay 结果（快照+B 分支重放） | 未交付 → L7 标注 `REPLAY_PENDING`，其他级别正常 | "L7 待 Replay 数据" |
| 全生命周期下钻报告（L7 运行态） | Trace（知识内容、推理引用、判定） | 推理事件缺失 → L7 证据链断裂，标注 `CHAIN_BROKEN` | "证据链不完整" |
| 消融测试报告 | Replay 结果 + 方差基线 | `unstable`/`non_replayable` case 排除，标注 `消融不可判定率` | "N% case 不可判定" |
| 归因分析报告 | L1-L7 下钻结果 + 因果链断点定位 | L7 不可判定 → 归因到 L6 为止，L7 相关归因标注 `INCONCLUSIVE` | "L7 归因不确定" |
| 归因分析报告（因果链） | Agent phase 标注 | 未标注 → 降级为 `inferred`，断点定位置信度降低 | "断点定位为推断" |
| 改进建议报告 | 归因分析报告 | 归因不确定 → 建议标注 `LOW_CONFIDENCE`，不输出高优先级建议 | "低置信建议" |
| 工具过程指标看板 | Trace（工具调用、Token、时间戳） | Trace 缺失 → 看板对应 Agent 标注 `NO_DATA` | "数据缺失" |

**降级传播规则**：降级沿依赖链传播——输入缺失 → 对应 L 级别标注 NA → 归因报告中该级别归因标注不确定 → 改进建议报告中相关建议降低优先级。每层降级在报告中显式标注，不静默跳过。

### 11.3 报告间依赖关系

```
端到端指标报告（基准）
    ↓ 依赖
全生命周期下钻报告（L1-L7）
    ↓ 依赖 L7 结果
消融测试报告 / 证据链分析报告
    ↓ 依赖 L1-L7 + 因果链
归因分析报告
    ↓ 依赖归因结果
改进建议报告
```

上游报告 NA 或降级时，下游报告同步降级（按§11.2 映射）。下游报告不能在上游报告缺失时独立产出——例如归因分析报告不能在生命周期下钻报告未产出时生成。

## 12. 约束与原则

| 约束 | 说明 |
|------|------|
| 禁止截断 | 数据过大时用聚合/压缩处理，不截断完整句子 |
| 禁止降级跳过 | 规则检测始终运行；分析失败时查清根因不跳过 |
| 根因分析铁律 | 所有归因和建议必须以真实数据为支撑 |
| 知识与记忆分开 | 两个独立后端系统，分析独立、指标独立 |
| 逐级下钻 | 7 级生命周期逐级下钻，精确定位断链位置，不跳级 |
| 责任主体明确 | 每条改进建议必须明确指向责任主体（工具/知识库/记忆/人工） |
| 消融测试排除死知识 | 开发态用 Replay A/B + JSD/Flip + 语义差异三层指标精确验证（含方差基线）；运行态用证据链分析（因果链推理，无反事实）；两者交叉验证 |
| Replay 协议化 | 评测引擎定义 replay 协议（快照点、A/B 分支、多轮重放、行为采集格式），各团队实现；运行态无 replay 时用证据链分析替代 |
| LLM 方差控制 | Replay 消融测试必须建立方差基线（多轮重放），JSD 差异需超出基线方差 k 倍才算"知识影响"；方差过大的 case 标记 `unstable` 不纳入统计 |
| 运行态 L7 方法论 | 运行态不用"LLM 模拟移除知识后推理"（LLM 已见过知识无法模拟"不知道"）；改用证据链分析——从 Trace 提取知识→推理引用→判定的因果链，程序化分析方向一致性 + LLM 判断知识正确性 |
| 结合工具实现 | 改进建议必须结合 Agent 的具体架构原理，不能泛泛而谈 |
| 两阶段推进 | 第一阶段聚焦误报率消减，第二阶段再关注漏报率 |
| 双模式闭环 | 开发态（基线集+replay）与运行态（生产+人工确认）互相补充；运行态产出新 case 补入开发态基线集 |
| 开发态门禁 | 开发态测评不达标阻断发布；运行态测评事后评估不阻断 |

### 12.1 指标阈值与门禁判定

开发态门禁需要明确的指标阈值。以下阈值基于第一阶段（误报率消减）目标设定，初始值为推荐值，需在首期测评后根据实际数据分布校准（遵循根因分析铁律——阈值基于实际数据，不凭空设定）：

| 指标 | 含义 | 门禁阈值 | 触发动作 | 初始值依据 |
|------|------|----------|----------|-----------|
| E2E FPR（KG） | KG 条件误报率 | ≤ NOGK 条件 FPR | 超出则阻断发布 | 核心目标：知识接入不应增加误报 |
| M25 负向知识率 | 知识误导导致误报的比例 | ≤ 15% | 超出则阻断发布 | 初始宽松，首期测评后校准 |
| M21 死知识率 | 召回但未使用的比例 | ≤ 30% | 超出则标记 warning（不阻断） | 死知识是浪费但不直接导致误报 |
| M22 行为影响率 | 知识实际产生效果的比例 | ≥ 40% | 低于则标记 warning | 与死知识率互补：影响率+死知识率+中性率≈100% |
| 消融不可判定率 | unstable/non_replayable 的比例 | ≤ 30% | 超出则标记 warning | 过高说明 replay 方案对该版本不适用 |
| M16 召回意识缺失率 | 需要知识但未发起访问的比例 | ≤ 20% | 超出则标记 warning | 召回意识不足是可改进的工程问题 |

**门禁判定逻辑**：

| 触发条件 | 判定 | 动作 |
|----------|------|------|
| E2E FPR（KG）> NOGK FPR **或** M25 > 阈值 | **阻断发布** | 不允许发布，改进建议标 high 优先级 |
| M21/M22/消融不可判定率/M16 超出阈值 | **警告** | 允许发布，但报告中标记 warning，改进建议标 medium 优先级 |
| 全部指标在阈值内 | **通过** | 正常发布 |

**阈值校准机制**：首期测评后，评测引擎统计各指标的实际分布（均值、中位数、P75、P90），基于分布重新校准阈值。校准后的阈值需人工确认后写入 `system_config` 表，后续测评按新阈值判定。阈值变更需递增 `_version` 字段（多 worker 部署同步）。

## 13. 数据需求与来源

本方案是 E2E 测评，每个指标的计算都需要具体数据支撑。以下按生命周期级别和因果链逐级列出：需要哪些数据字段、数据格式、来源系统、采集方式。

### 13.1 端到端测评数据

| 数据 | 字段/格式 | 来源系统 | 采集方式 |
|------|----------|----------|----------|
| 基线 case 集 | case_id, vulnerability_type, source_file, sink_file, sink_line, expected_label (TP/FN), confirmation_status | V-Bench zip / 漏洞中心 Chimera | 评测引擎 INGESTING 阶段拉取 |

| 人工确认结果 | case_id, confirmation_status (vulnerable/not_vulnerable), confirmed_by, confirmed_at | 漏洞中心 Chimera | 评测引擎 API 拉取（运行态） |
| KG/NOGK 条件标识 | run_condition (KG/NOGK/UNKNOWN), run_id, task_id | 评测引擎 | 评测引擎在创建评测时设置 |

### 13.2 L1-L7 生命周期数据

#### L1：是否需要知识/记忆

| 数据 | 字段/格式 | 来源系统 | 采集方式 |
|------|----------|----------|----------|
| 基线漏洞类型分布 | vulnerability_type, count | 基线 case 集 | 评测引擎统计 |

| 漏洞类型复杂度分级 | vulnerability_type, complexity_level (high/medium/low), reason | 评测引擎 | 评测引擎预定义分级表（反序列化/SSRF/跨文件=高，简单语法级=低） |
| 基线 case 标注 | case_id, requires_knowledge (bool/undetermined) | 基线 case 集 | 基线集标注（人工或自动） |
| 知识需求判定结果 | case_id, needs_knowledge (yes/no/undetermined), reason | 评测引擎 | 评测引擎基于历史误判率 + 复杂度分级 + 基线标注综合判定 |

#### L2：发起知识/记忆访问

| 数据 | 字段/格式 | 来源系统 | 采集方式 |
|------|----------|----------|----------|
| 知识访问事件 | event_id, timestamp, agent_name, access_type (knowledge_base/memory/evolution), query_text, session_id | 挖掘/验证 Agent Trace | Trace 解析——识别知识访问工具调用（wiki 查询、skill 调用、memory read 等） |
| 访问发起标识 | case_id, has_knowledge_access (bool), access_event_list | 评测引擎 | 评测引擎从 Trace 解析结果中提取 |

**关键改造**：Agent Trace 中必须能区分访问的是知识库、记忆模块还是进化模块。当前 Trace 可能不区分或未记录访问类型。

#### L3：知识/记忆查询

| 数据 | 字段/格式 | 来源系统 | 采集方式 |
|------|----------|----------|----------|
| 查询内容 | query_id, query_text, query_context (代码上下文), agent_name, timestamp | 挖掘/验证 Agent Trace | Trace 解析——从知识访问事件的参数中提取 |
| 查询准确性判定 | query_id, accuracy (accurate/vague/wrong), reason | 评测引擎 | 评测引擎 LLM 判断（query vs 基线漏洞信息） |

#### L4：知识/记忆存在

| 数据 | 字段/格式 | 来源系统 | 采集方式 |
|------|----------|----------|----------|
| 知识返回内容 | query_id, response_text, response_source (knowledge_base/memory/evolution), response_status (non_empty/empty), content_length | 知识库/记忆/进化 | Trace 解析——从工具调用的返回结果中提取 |
| 知识存在判定 | query_id, knowledge_exists (bool), source_system | 评测引擎 | 评测引擎基于 response_status 判定 |

**关键改造**：知识库、记忆模块、进化模块的返回结果需要在 Trace 中可区分。当前 Trace 可能将三者混在一起或未标记来源。

#### L5：知识/记忆召回

| 数据 | 字段/格式 | 来源系统 | 采集方式 |
|------|----------|----------|----------|
| 召回状态 | query_id, recall_success (bool), failure_reason (transport_error/parse_error/format_incompatible/null) | 评测引擎 | 评测引擎基于 Trace 中工具调用是否成功获取并解析返回内容判定 |
| 召回内容摘要 | query_id, recalled_content_summary | 评测引擎 | 评测引擎从 response_text 中提取摘要 |

#### L6：知识/记忆使用

| 数据 | 字段/格式 | 来源系统 | 采集方式 |
|------|----------|----------|----------|
| 推理文本 | event_id, timestamp, reasoning_text (thinking/reasoning 事件内容), agent_name | 挖掘/验证 Agent Trace | Trace 解析——提取知识召回之后的推理事件 |
| 知识引用标识 | query_id, is_referenced (bool), reference_evidence (推理文本中引用知识的片段) | 评测引擎 | 评测引擎 LLM 判断推理文本是否引用了召回的知识内容 |

**关键改造**：Agent Trace 中推理事件（thinking/reasoning）需完整记录。部分 Agent 可能未输出推理过程或推理过程未记录到 Trace。

#### L7：知识/记忆影响推理

**开发态（Replay 消融测试）**：

| 数据 | 字段/格式 | 来源系统 | 采集方式 |
|------|----------|----------|----------|
| 快照点数据 | snapshot_id, case_id, agent_name, timestamp, code_context, tool_call_history, agent_state, knowledge_response_content | 挖掘/验证 Agent | Agent 在知识召回时刻保存快照 |
| A 分支行为轨迹 | snapshot_id, branch (A), tool_call_sequence, reasoning_text, final_judgment | 挖掘/验证 Agent | Agent 重放（保留知识返回内容） |
| B 分支行为轨迹 | snapshot_id, branch (B), tool_call_sequence, reasoning_text, final_judgment | 挖掘/验证 Agent | Agent 重放（置空知识返回内容） |
| JSD 值 | snapshot_id, jsd_value | 评测引擎 | 评测引擎对 A/B 工具调用分布计算 |
| Flip 结果 | snapshot_id, flip (bool), a_judgment, b_judgment | 评测引擎 | 评测引擎比较 A/B 最终判定 |
| LLM 语义分析结果 | snapshot_id, semantic_diff (bool), reason | 评测引擎 | JSD≤阈值 且 Flip=True 时 LLM 辅助判断 |

**运行态（证据链分析）**：

| 数据 | 字段/格式 | 来源系统 | 采集方式 |
|------|----------|----------|----------|
| 知识召回内容 | case_id, knowledge_content, knowledge_source (knowledge_base/memory/evolution) | 评测引擎 | 评测引擎从 Trace 中提取知识返回内容 |
| 推理引用片段 | case_id, reference_text (推理文本中引用知识的片段), reference_position | 评测引擎 | L6 分析结果——推理文本中引用知识的位置 |
| 判定结论 | case_id, final_judgment (finding/verdict), judgment_direction (is_vuln/not_vuln) | 评测引擎 | 评测引擎从 Trace 中提取 Agent 最终判定 |
| 知识方向分析 | case_id, knowledge_direction (points_to_vuln/points_to_safe/neutral) | 评测引擎 | 评测引擎程序化分析知识内容方向 |
| 方向一致性 | case_id, direction_consistency (consistent/inconsistent) | 评测引擎 | 评测引擎比较知识方向 vs 判定方向 |
| 知识正确性判定 | case_id, knowledge_correctness (correct/incorrect/partially_correct) | 评测引擎 LLM | LLM 对比知识内容与基线漏洞信息 |
| L7 效果判定 | case_id, effect (positive/negative/neutral), confidence (high/medium/low), reason | 评测引擎 | 评测引擎基于方向一致性 + 知识正确性推理 |
| 因果链证据 | case_id, evidence_chain (knowledge_content → reference_text → judgment), chain_completeness (complete/broken) | 评测引擎 | 评测引擎组装证据链 |

### 13.3 因果链分层数据

| 数据 | 字段/格式 | 来源系统 | 采集方式 |
|------|----------|----------|----------|
| 挖掘 Agent 工具调用序列 | call_id, timestamp, tool_name, tool_params, tool_result, session_id | 挖掘 Agent Trace | Trace 解析——提取工具调用事件序列 |
| 验证 Agent 工具调用序列 | call_id, timestamp, tool_name, tool_params, tool_result, session_id | 验证 Agent Trace | Trace 解析——提取工具调用事件序列 |
| 挖掘↔验证 Trace 关联 | case_id, mining_session_id, verify_session_id, finding_id (挖掘产出→验证输入) | 评测引擎 | 评测引擎通过 `session_graph` 表 parent_id 边关联挖掘 session 和验证 session（同一 finding_id） |
| 因果链断点判定 | case_id, breakpoint_stage (entry_identification/dataflow_tracking/pattern_recognition/sink_localization/judgment_reporting/vuln_understanding/code_localization/verification_execution), reason, confidence (labeled/inferred) | 评测引擎 | 评测引擎基于 Agent phase 标签（labeled）或工具调用推断（inferred）定位断点 |
| Agent phase 标注 | event_id, phase (entry_identification/dataflow_tracking/...), timestamp | 挖掘/验证 Agent Trace | Agent 在推理事件中主动标注 phase 字段 |
| 交叉归因结果 | case_id, breakpoint_stage, lifecycle_level (L1-L7), responsibility_subject | 评测引擎 | 评测引擎交叉矩阵计算 |

**挖掘↔验证 Trace 关联说明**：一个任务的挖掘 Agent 产出 finding，验证 Agent 验证该 finding。两类 Trace 有时序依赖——验证 Agent 读取挖掘 Agent 的 finding 描述作为输入。评测引擎通过 `session_graph` 表的 parent_id 边关联同一 case 的挖掘 session 和验证 session（挖掘 session 是验证 session 的 parent）。L1-L7 分析分别对挖掘 Trace 和验证 Trace 独立执行，因果链分析按"挖掘 5 阶段 → 验证 4 阶段"串联——先定位挖掘 Trace 中的断点，如挖掘阶段无断点再定位验证 Trace 中的断点。

### 13.4 资源效率数据

| 数据 | 字段/格式 | 来源系统 | 采集方式 |
|------|----------|----------|----------|
| Token 消耗 | agent_name, total_tokens, prompt_tokens, completion_tokens, per_call_breakdown | 挖掘/验证 Agent Trace | Trace 解析——从 LLM 调用事件的 usage 字段提取 |
| 步数 | agent_name, step_count, per_tool_call_count | 评测引擎 | 评测引擎统计 Trace 中工具调用事件数 |
| 耗时 | agent_name, total_duration_ms, per_phase_duration | 评测引擎 | 评测引擎从 Trace 时间戳计算 |

### 13.5 数据完整性与时序对齐

**数据完整性校验**：测评启动前，评测引擎对输入数据做完整性校验。缺失数据不跳过分析，而是按以下规则处理：

| 缺失数据 | 影响范围 | 处理方式 | 报告标注 |
|----------|----------|----------|----------|
| Trace 中无推理事件（thinking/reasoning） | L6 知识使用率无法判定 | L6 标注 `DATA_MISSING`，L7 相应无法判定 | "推理事件缺失，L6/L7 不可判定" |
| Trace 中无 phase 标注 | 因果链断点定位降级 | 降级为工具调用推断（`inferred`），置信度降低 | "phase 标注缺失，断点定位为推断" |
| Trace 中知识访问未标记目标系统 | L2-L4 无法按三系统独立统计 | 降级为二分法（KG/Memory），进化部分标记 `UNIDENTIFIED_SOURCE` | "知识来源未区分，进化统计为空" |
| Replay 结果未交付 | L7 开发态无法判定 | L7 标注 `REPLAY_PENDING`，其他级别正常执行 | "Replay 数据待交付，L7 开发态待定" |
| 人工确认结果未就绪（运行态） | E2E FPR/FNR 无法计算 | 阻塞运行态测评启动——E2E 指标是全部分析的基准 | 不启动，等数据就绪 |

**时序对齐**：运行态测评需要"Agent Trace + 人工确认结果 + 漏洞中心 case 数据"三者就绪后触发。三者产出时间不同步——Agent Trace 在项目测试完成时即有，人工确认可能延后数周。人工触发前需确认三者全部就绪。开发态测评数据来源固定（基线集 + Agent Trace + Replay 结果），无时序对齐问题，但 Replay 结果需按 SLA 交付（§10.2）。

### 14.3 验证 Agent 改造（2 个）

验证 Agent 的改造需求与挖掘 Agent 相同（Trace 知识访问标记、推理事件完整记录、phase 标注、Replay 能力），但业务流程阶段和 Replay 差异点不同：

| 差异点 | 挖掘 Agent | 验证 Agent |
|--------|-----------|-----------|
| Replay 快照点 | 知识返回后的下一个推理步开始前（漏洞挖掘流程中） | 知识返回后的下一个推理步开始前（漏洞验证流程中） |
| A 分支判定结果 | finding（是否提交漏洞报告） | verdict（confirmed / ruled_out） |
| B 分支判定结果 | 同 A 分支比较 finding | 同 A 分支比较 verdict |
| 因果链阶段 | 入口识别/数据流追踪/模式识别/Sink定位/判定上报 | 漏洞理解/代码定位/验证执行/判定上报 |
| phase 字段值 | entry_identification / dataflow_tracking / pattern_recognition / sink_localization / judgment_reporting | vuln_understanding / code_localization / verification_execution / judgment_reporting |

验证 Agent 的 Replay 快照需要保存的上下文与挖掘 Agent 不同：
- 验证 Agent 快照需包含：finding 描述、已定位的代码位置、已构造的 PoC 状态
- A/B 分支重放后比较的是 verdict（confirmed/ruled_out），不是 finding

### 14.4 知识库改造

知识库是被测评的三个独立系统之一，需提供覆盖度和质量数据。

| 改造项 | 说明 | 对应指标 | 优先级 |
|--------|------|----------|--------|
| 覆盖度 API | 提供接口查询哪些漏洞类型有知识、哪些没有。返回 `vulnerability_type` → `has_knowledge (bool)` + `knowledge_id_list` | L1 知识需求率、L4 知识库存在率 | high |
| 知识内容质量数据 | 提供知识内容的准确性标注（知识是否正确、是否过时） | L4 知识库存在率、E2E 知识库负向率 | medium |
| 返回内容来源标记 | 知识库返回结果中增加来源标识，使 Trace 中可区分知识库返回 vs 记忆返回 vs 进化返回 | L4 三系统独立统计 | high |
| 知识版本管理 | 知识变更版本化，支持开发态控制变量实验（同基线集对不同知识版本做对照） | 开发态 KG vs NOGK 对照 | medium |

**覆盖度 API 用途说明**：覆盖度 API 不直接参与 L1 判定（L1 基于历史误判率推断，不依赖知识库侧的覆盖度数据）。覆盖度 API 的核心用途有两处：(1) **L4 归因解释**——当 L4 判定为"知识缺失"时，用覆盖度 API 确认该漏洞类型确实在知识库中未收录（而非知识库有知识但 Agent 未查到），区分"知识库覆盖不足"和"Agent 查询方向错误"两类断链原因；(2) **改进建议归因**——当改进建议指向知识库团队时，覆盖度数据提供"哪些漏洞类型需要补充知识"的具体清单。

### 14.6 进化模块改造

进化模块是第三个独立系统，需独立提供数据。**进化模块的改造是一切三系统独立统计的前置条件**——当前进化模块的调用接口尚未定义，评测引擎 parser 无法识别进化模块访问。进化模块团队需先完成接口定义，各 Agent 才能按接口实现调用，评测引擎才能做 parser 识别。

| 改造项 | 说明 | 对应指标 | 优先级 |
|--------|------|----------|--------|
| **调用接口定义（前置阻塞项）** | 定义进化模块的调用接口和返回格式（CLI 命令/API 端点/MCP 工具），使 Agent 可调用且评测引擎 parser 可识别 | 所有进化相关指标 | **blocking** |
| 覆盖度 API | 提供接口查询进化知识覆盖哪些漏洞类型 | L4 进化知识存在率 | high |
| 产出记录 API | 提供进化知识产出记录（何时产出、从哪些历史经验提炼、产出什么知识） | L4 进化知识存在率、E2E 进化负向率 | high |
| 返回内容来源标记 | 进化模块返回结果中增加来源标识，使 Trace 中可区分 | L4 进化独立统计 | high |
| 进化知识质量数据 | 提供进化知识的准确性标注（进化产出的知识是否正确、是否引入误导） | E2E 进化负向率 | medium |

### 14.7 改造优先级与依赖关系

改造分三期推进：

| 期次 | 改造内容 | 依赖 | 产出 |
|------|----------|------|------|
| 第一期（基础数据） | 评测引擎 RawEvent 三分法 + KnowledgeInteractionFact 扩展 + 各 Agent Trace 知识访问标记 + 推理事件完整记录 + phase 标注 + 三系统返回内容来源标记 | 无 | L1-L6 生命周期分析可执行 + 因果链断点定位可执行（labeled 模式） |
| 第二期（因果链 + 运行态 L7） | 因果链分析模块 + 交叉归因模块 + 证据链分析模块 | 第一期 | 运行态完整测评（L7 证据链分析，无 replay） |
| 第三期（Replay 消融） | 各 Agent 快照 + B 分支多轮重放 + 行为采集 + 评测引擎 Replay 执行引擎 + 方差基线 + JSD/Flip 计算 | 第一期 | 开发态完整测评（L7 replay 精确模式） |

**为什么这样排**：

- **第一期先做 L1-L6**：L1-L6 不依赖 replay，数据来源是 Trace 离线分析（推理文本、知识访问事件、返回内容），评测引擎已有 parser 基础设施。L1-L6 本身有独立价值——过程指标可定位断链发生在哪一级（如 L2 召回意识缺失、L4 知识缺失、L6 死知识），各团队可立即据此改进。L1-L6 的局限是无法区分"使用了但未影响"（L7 无效知识）和"影响了但方向恰好一致"——这个区分需要 L7，但不阻塞 L1-L6 的产出。
- **第二期做因果链 + 运行态 L7**：因果链分析依赖第一期的 phase 标注（Agent 改造完成）。运行态 L7 证据链分析不依赖 replay（不需要 Agent 做 B 分支重放），只需评测引擎从 Trace 中提取知识→推理引用→判定的因果链。运行态可先落地，因为它不需要 Agent 团队做 replay 改造（改造量最大）。
- **第三期做 Replay 消融**：Replay 需要 Agent 实现快照 + B 分支多轮重放 + 行为采集，改造量和技术复杂度最大。但 L7 是核心创新点——只有 replay 能做反事实推理，区分"知识影响了判定"和"即使没有知识也会得出相同判定"。第一期和第二期积累的 case 数据和运行态 L7 证据链分析结果，可以作为第三期 replay 的输入和交叉验证基线。

```
第一期（基础数据）
  ├── 评测引擎: RawEvent 三分法 + KnowledgeInteractionFact 扩展
  ├── 各 Agent: Trace 知识访问标记 + 推理事件完整记录 + phase 标注
  ├── 知识库/记忆/进化: 返回内容来源标记
  └── 产出: L1-L6 可执行 + 因果链断点定位可执行
      ├── 独立价值: 过程指标定位断链位置（L2 召回意识/L4 知识缺失/L6 死知识）
      └── 局限: 无法区分"使用了但未影响"和"影响了但方向恰好一致"
                    ↓
第二期（因果链 + 运行态 L7）
  ├── 评测引擎: 因果链分析 + 交叉归因 + 证据链分析
  └── 产出: 运行态完整测评（L7 证据链分析）
      ├── 价值: 运行态可先落地（不需 Agent replay 改造）
      └── 局限: L7 证据链分析无法排除"恰好方向一致"的假阳性
                    ↓
第三期（Replay 消融）
  ├── 各 Agent: 快照 + B 分支多轮重放 + 行为采集
  ├── 评测引擎: Replay 执行引擎 + 方差基线 + JSD/Flip/语义差异计算
  └── 产出: 开发态完整测评（L7 replay 精确模式）
      ├── 价值: 反事实推理，精确区分死知识和无效知识
      └── 交叉验证: 第一期+第二期的 case 数据和证据链分析结果作为 replay 结果的对照基线
```
