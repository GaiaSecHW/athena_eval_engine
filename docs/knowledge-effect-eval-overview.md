# 奇美拉误报归因与改进测评方案

## 0 背景：奇美拉系统现状与测评范围

### 0.1 奇美拉系统架构

奇美拉是一个 AI 驱动的漏洞挖掘系统，漏洞挖掘流程为：

> **大模型 + 漏洞挖掘 + 漏洞验证 + 知识库/记忆进化 = 漏洞**

| 组件 | 角色 |
|------|------|
| 大模型（LLM） | 推理引擎，驱动挖掘与验证的全流程 |
| 漏洞挖掘 Agent | 4 个 Agent（Turing、Argo、SecMate、DataflowVulnScan），负责入口识别→数据流追踪→漏洞模式识别→Sink 定位→判定上报 |
| 漏洞验证 Agent | 2 个 Agent（CVulnVerify、WebVulnVerify），负责漏洞理解→代码定位→验证执行→判定上报 |
| 知识库/记忆进化 | 知识库 + 记忆进化模块，为挖掘和验证提供漏洞模式、历史经验、产品文档等 |

**按组件汇总**（一个误报可能涉及多个组件，故各组件占比有交叉）：

| 组件 | 累计占比 | 典型问题 |
|------|---------|---------|
| 大模型 | 1.1% | 幻觉调用链（C6） |
| 漏洞挖掘 | 50.2% | 重复上报、入口不可达、参数误判、未验证调用链、未识别测试代码 |
| 漏洞验证 | 68.4% | 框架防御未识别、已有校验未排除、配置/业务设计误判、测试代码未识别、未验证调用链真实性、未验证入口可达性、未验证参数可控性 |
| 知识库/记忆进化 | 67.3% | C2/C3/C4/C7/C8/C9/C10 中知识缺失或有误——当前无法量化，正是本方案要解决的 |

**误报率超 30%**。从上表可以看出：知识库/记忆进化贯穿 C2/C3/C4/C7/C8/C9/C10 七类误报（C1/C5/C6 除外）——C7（框架自带防御 291 条）和 C3（已有校验 41 条）最典型，如果知识库里有"该框架自带输入过滤"的知识，验证 Agent 就不会误判为漏洞。但当前无法量化知识库/记忆进化到底贡献了多少误报，这正是本方案要解决的问题。

### 0.3 测评范围推导

从 0.2 节误报表可以看出：

1. **大模型**仅涉及 C6（幻觉调用链，1.1%）。幻觉问题的改进只能靠模型升级，不属于漏洞挖掘团队的可改进项。大模型涉及误报占比极低（1.1%），且无可通过测评驱动改进。

2. **漏洞挖掘**占 50.2%，**漏洞验证**占 68.4%，两者合计覆盖绝大多数误报。这两个组件是 Agent 团队可改进的——改进查询策略、增加知识触发点、优化判定逻辑等。

3. **知识库/记忆进化**占 67.3%，贯穿 C2/C3/C4/C7/C8/C9/C10 七类误报。知识缺失或有误是可改进的——补充知识、修正过时知识、标记适用区间。但当前无法量化知识库/记忆进化到底贡献了多少误报，这正是本方案要解决的问题。

因此，本方案分长期与短期两条路径：

| 路径 | 范围 | 改进手段 | 典型误报 | 特点 |
|------|------|---------|---------|------|
| 长期方案 | 大模型 | 跟随业界主流大模型进行升级，提升推理能力（减少幻觉） | C6 幻觉调用链（1.1%） | 效果上限高——模型升级一次，全局受益 |
| 短期方案 | 漏洞挖掘 + 漏洞验证 + 知识库/记忆进化 | Agent 改进（增加知识触发点、优化查询策略、改进判定逻辑、去重逻辑）+ 知识库/记忆进化改进（补充缺失知识、修正有误知识、标记适用区间） | C1–C10（100%） | 可定位、可改进、可回归验证，周期短，见效快——知识补一条就少一类误报 |

**两条路径互补**：长期方案解决大模型自身的推理能力上限问题，短期方案在现有模型能力下挖掘"漏洞挖掘 + 漏洞验证 + 知识库/记忆进化"链路的改进空间。

本方案的测评范围聚焦**短期方案**——漏洞挖掘 + 漏洞验证 + 知识库/记忆进化三个组件的全链路归因，定位误报根因在这条链路的哪个环节、哪个级别，驱动针对性改进。

## 1 要解决什么问题

V2 评测引擎已实现 L0–L7 误报根因全链路分析、因果链断点分析、有效 case 筛选。已能回答"误报根因在哪"、"知识有没有用"、"谁的责任"。

**尚缺**：

- 误报**升了还是降了**——缺乏召回率 + 准确率指标从漏洞中心终审数据量化整体趋势
- **改了有效吗**——缺乏 DTS 问题单系统驱动 case 级根因定位与回归验证闭环
- case 级根因定位——哪个 case 误报/漏报、跨了哪些 session、根因发生在哪个 session

## 3 误报根因在哪：知识使用全链路 L0–L7

一个误报 case 从"需不需要知识"到"知识是否影响了判定"，**L0–L7 共 8 级**。L0 标记知识的原始来源（用户上传/历史漏洞经验/已有知识升华等），不产生断链；L1 为前置判定，不产生断链；L2–L7 逐级往下，每一步都可能断。**断在哪一步，就是哪种成因**，对应不同责任方和改进动作。

### 3.1 八级链条

| 级别 | 追问 | 断了是什么成因 | 含义 | 责任方 |
|------|------|---------------|------|--------|
| L0 | 知识来源？ | — | 知识内容的原始来源（用户上传/历史漏洞经验/已有知识升华等），仅标记 provenance，不产生断链 | — |
| L1 | 需要知识？ | — | 场景是否需要知识支撑（前置判定，不产生断链） | — |
| L2 | 发起访问？ | A 该查没查 | 需要知识但没发起访问，召回意识不足 | Agent |
| L3 | 查询准确？ | B 查询太泛/不聚焦 | 查询内容过于宽泛，没有聚焦到当前 case 的具体漏洞类型和技术栈 | Agent |
| L4 | 知识存在？ | C 查了没得 | 知识库/记忆进化里没有，覆盖度不足 | 知识方 |
| L5 | 成功取回？ | D 链路问题 | 工具失败/超时/解析错误 | Agent + 知识方 |
| L6 | 被使用？ | E 查到没用 | 召回了但推理没引用，死知识 | Agent |
| L7 | 影响结论？ | F 用了没推动 / G 导致误判 | F：引用了但没改变结论，无效知识 / G：知识推动了判定但方向错了（知识内容有误/过时/不适用），负向知识 | F: Agent / 知识方，G: 知识方 |

**L7 判定方法**：提取知识内容、推理引用片段、判定结论，用 LLM 做离线分析——知识正确性（对比基线漏洞信息：漏洞类型/描述/sink 点）× 方向一致性（知识方向 vs 判定方向）→ 三种效果：正确+一致=正向，错误+一致=负向（G），不一致=中性（F）。LLM 无法确认时标 `l7_influenced=NULL`。

每个误报 case 在 Agent 级别做 L0–L7 判定，一个 case 可能有多个断点。以下矩阵展示各 Agent 在不同 L 级别断链时的典型成因：

| Agent | L2 断（A 该查没查） | L3 断（B 查询太泛） | L4 断（C 查了没得） | L5 断（D 链路问题） | L6 断（E 查到没用） | L7 断（F 用了没推动） | L7 负向（G 导致误判） |
|-------|---|---|---|---|---|---|---|
| Turing | 未发起知识访问 | 查询未聚焦 | 知识不存在 | 工具超时 | 召回知识但未引用 | 知识未影响判定 | 知识误导 |
| Argo | 未发起知识访问 | 查询未聚焦 | 知识不存在 | 工具超时 | 召回知识但未引用 | 知识未影响判定 | 知识误导 |
| SecMate | 未发起知识访问 | 查询未聚焦 | 知识不存在 | 工具超时 | 召回知识但未引用 | 知识未影响判定 | 知识误导 |
| DataflowVulnScan | 未发起知识访问 | 查询未聚焦 | 知识不存在 | 工具超时 | 召回知识但未引用 | 知识未影响判定 | 知识误导 |
| CVulnVerify | 未发起知识访问 | 查询未聚焦 | 知识不存在 | 工具超时 | 召回知识但未引用 | 知识未影响判定 | 知识误导 |
| WebVulnVerify | 未发起知识访问 | 查询未聚焦 | 知识不存在 | 工具超时 | 召回知识但未引用 | 知识未影响判定 | 知识误导 |

## 5 两种触发时机：开发态与运行态

同一套分析流程（L0–L7 + 因果链 + 归因），差异在于**触发时机**和**数据来源**：

| 维度 | 开发态 | 运行态 |
|------|--------|--------|
| 触发时机 | Agent 发布新版本 | 项目测试完成 |
| 基线来源 | 预置基线集（V-Bench / 漏洞中心已确认 case） | 漏洞中心人工确认结果 |
| 分析 case 类型 | FP（误报）+ FN（漏报） | 只 FP（误报） |
| 分析方法 | L0–L7 全链路判定（详见第 3 节） | L0–L7 全链路判定（详见第 3 节） |
| 门禁 | 不达标可阻断发布 | 误报率 > 30% 时触发预警，提醒是否进入测评分析 |

**协作闭环**：运行态发现的问题案例补入开发态基线集 → 下轮开发态验证是否改善 → 改进后发布 → 触发下一轮运行态测评。

### 5.1 有效 case 筛选规则

两种触发时机都从**漏洞中心人工确认数据**出发，但 FP 和 FN 的筛选流程不同：

**FP（误报）筛选**：
1. 基线标注 `expected_label=NON_VULNERABLE` 的 case
2. 在 trace findings 中找对应 finding
3. 找到且 `validation_result=CONFIRMED` → agent 误报了漏洞
4. 从漏洞中心终审数据提取 `human_confirmation.false_positive_reason`，映射为 C1-C10 误报类型（详见需求文档 4.3.1 节）

**FN（漏报）筛选**（仅开发态）：
1. 基线标注 `expected_label=VULNERABLE` 的 case
2. 将基线漏洞与**告警中心**数据对比
3. 告警中心有匹配 → agent 上报了该漏洞，不是漏报，跳过
4. 告警中心无匹配 → agent 漏报了该漏洞
5. 对漏报的 case，提取 sink 点，用 LLM 匹配在 trace 中找对应 session

**FP 的匹配方式**取决于基线来源（`benchmark_source`）：

| 基线来源 | 匹配方式 | 说明 |
|----------|---------|------|
| 漏洞中心（`vuln_center`） | 纯代码匹配 | finding_id 直接匹配 → 标题匹配 → 内容匹配，不需要 LLM |
| V-Bench 测评集（`vbench_zip`） | LLM 匹配 | 两阶段（标题预筛 → 1vs1 详细对比），复用 v1 `fpr_analysis.py` 的方法 |

**FN 的匹配方式**：
- 基线漏洞 vs 告警中心：与 FP 相同的匹配方式（vuln_center 纯代码，vbench_zip LLM）
- 漏报 case vs trace：始终用 LLM 匹配（因为漏报意味着 trace 里没有 finding，只能用 sink 点信息定位 session）

**找不到对应 trace 的 case**：在报告中告警，不参与分析。

**跨 session case**：一个 case 在 Agent 内部可能跨多个 session（入口识别→数据流追踪→漏洞模式识别→Sink 定位→判定上报，每步可能独立 session），session 间的 parent-child 调用关系存储在各 Agent 自己的数据库中，评测引擎通过 `agent_datasource_config` 配置的关系表直连 Agent DB 查询。按 `task_id` 分组，组级别判定 FP/FN，组内保留有知识访问的 task_run。

## 6 指标体系

指标分两层：**最终结果指标**面向领导，从漏洞中心终审数据计算召回率和准确率，驱动平台能力的持续迭代；**case 级根因定位**面向工程团队，通过 DTS 问题单定位每个误报/漏报 case 的根因发生在哪个 session。

**只对有效 case 内的知识访问做分析**：

| 触发时机 | 有效 case 标准 |
|----------|--------------|
| 开发态 | FP（误报）：基线 NON_VULNERABLE，trace 有对应 finding 且 CONFIRMED；FN（漏报）：基线 VULNERABLE，告警中心无匹配，用 sink 在 trace 中定位到 session |
| 运行态 | 只 FP（误报）：基线 NON_VULNERABLE，trace 有对应 finding 且 CONFIRMED |

匹配方式和筛选流程详见 5.1 节。

### 6.1 最终结果指标（面向领导）

从漏洞中心终审数据直接计算：

| 指标 | 定义 | 数据来源 |
|------|------|---------|
| 召回率 | TP / (TP + FN) | 漏洞中心终审（confirmation_status=vulnerable 的基线 case 中 Agent 上报的比例） |
| 准确率 | TP / (TP + FP) | 漏洞中心终审（Agent 上报的 finding 中漏洞中心确认是真漏洞的比例） |

### 6.2 case 级根因定位（面向工程团队）

不做指标聚合，通过 DTS 问题单逐 case 定位：

| 内容 | 说明 |
|------|------|
| 哪个 case 是误报/漏报 | 从有效 case 筛选结果获取 |
| 跨了哪些 session | 通过 `agent_datasource_config` 配置的关系表直连 Agent DB 查询 session 调用链 |
| 根因是什么 | L0–L7 全链路判定，定位断点级别和成因（A–G） |
| 根因发生在哪个 session | 断点对应的 session_id，记录在 knowledge_access_detail 中 |

## 7 各系统改造需求

本方案是 E2E 测评，涉及的系统按需改造。

### 7.1 评测引擎

| 改造项 | 说明 |
|--------|------|
| L0–L7 误报根因全链路分析模块 | 新建逐级下钻分析逻辑（含 L7 方向一致性 + 知识正确性判定） |

| 报告段扩展 | 新增 lifecycle 报告段（含因果链分析） |

### 7.2 DTS 问题单系统

| 改造项 | 说明 |
|--------|------|
| DTS 问题单管理 | 评测引擎自动生成 DTS 单（责任方 + 成因 + 误报类型 + 断点描述 + 证据），责任方（Agent 或知识方）在 DTS 单详情页查看证据、定位根因、填写解决方案、操作状态 |

## 8 端到端案例：一个误报如何锁定根因并改进

一个 FP case 在 Agent 级别做 L0–L7 判定，可能存在多个断点。统计单元 = 每次知识访问，一个 case 可能有多条知识访问记录，每条独立判定 L0–L7。以下展示一个含两个断点的误报案例：

### 8.1 场景

Turing 对某项目进行漏洞挖掘。基线标注该 case 为 `NON_VULNERABLE`（非漏洞），但 Turing 上报了漏洞（`validation_result=CONFIRMED`），构成 FP。该 case 涉及两次知识访问机会：

- **访问 1**：Turing 查询了知识库中关于"Spring 框架 SQL 注入防护"的知识，知识返回内容称"该框架无内置防护"，Turing 据此判定为漏洞。实际上该框架在新版本已添加防护，知识内容过时。
- **访问 2**：Turing 在判定参数可控性时，本应查询知识库中"参数来源约束"相关知识，但未发起查询。

### 8.2 数据采集阶段（INGESTING + PARSING）

**输入**：Agent Trace（JSONL/SQLite）+ 基线数据（漏洞中心）+ 告警中心数据

**产出**：

| 数据 | 内容 |
|------|------|
| RawEvents | Turing 的全部 trace 事件，含 REASONING（推理文本）、TOOL（工具调用）、KG（知识访问）等 |
| KnowledgeInteractionFact | 访问 1 的交互记录：command="Spring SQL注入防护"，output_preview="该框架无内置防护..." |
| OutcomeFact | FP（误报），validation_result=CONFIRMED |
| BenchmarkItem | expected_label=NON_VULNERABLE，vulnerability_type=SQL注入 |

### 8.3 生命周期分析阶段（LIFECYCLE_ANALYSIS）

**输入**：RawEvents + KnowledgeInteractionFact + OutcomeFact + BenchmarkItem

**产出**：`knowledge_access_detail` 表，每次知识访问一条记录

**访问 1 的 L0–L7 判定**：

| 级别 | 判定 | 方法 | 依据 |
|------|------|------|------|
| L0 | 来源=人工 | 程序（frontmatter `来源` 字段） | 知识条目 frontmatter |
| L1 需要？ | ✓ | LLM | 推理上下文涉及框架防护判断 |
| L2 发起？ | ✓ | 程序 | `is_kg_interaction=True` |
| L3 准确？ | ✓ | LLM | 查询"Spring SQL注入防护"聚焦到当前漏洞类型 |
| L4 存在？ | ✓ | 程序 | 返回内容非空 |
| L5 取回？ | ✓ | 程序 | 工具无报错/超时 |
| L6 引用？ | ✓ | LLM | REASONING 文本引用了"该框架无内置防护" |
| L7 影响？ | ✓ 推动但方向错 | LLM | 知识方向=漏洞，判定方向=漏洞，但知识内容过时→方向错 |

→ 成因 G（导致误判，知识内容有误），效果标签=负向，责任方=知识方

**访问 2 的 L0–L7 判定**：

| 级别 | 判定 | 方法 | 依据 |
|------|------|------|------|
| L1 需要？ | ✓ | LLM | 参数可控性判断需要知识支撑 |
| L2 发起？ | ✗ | 程序 | 无 `is_kg_interaction=True` 的事件 |

→ 成因 A（该查没查），效果标签=中性，责任方=Agent

### 8.4 因果链分析阶段（CAUSAL_CHAIN）

**输入**：`knowledge_access_detail` 表（已含 agent_type + L1–L7 判定 + cause_code）

**产出**：

| 数据 | 内容 |
|------|------|
| 交叉归因矩阵 | Turing × L2=1（A）× L7=1（G） |
| 断点清单 | case 有 2 个断点：断点 1 断在 L7（G），断点 2 断在 L2（A） |
| DTS 问题单 | 2 条（见下） |

### 8.5 DTS 问题单生成

**输入**：因果链分析产出的断点清单

**产出**：

| DTS 单 | 责任方 | 成因 | 断点 | 误报类型 | 内容 |
|--------|--------|------|------|---------|------|
| ① | 知识方 | G | L7 | C7 框架/组件自带防御 | "Spring SQL注入防护"知识内容过时，框架新版本已添加防护，需更新知识内容并标记适用版本区间 |
| ② | Turing | A | L2 | C7 框架/组件自带防御 | Turing 在判定参数可控性时未发起知识查询，需增加知识触发点 |

### 8.6 改进与回归验证

**输入**：DTS 问题单 + 责任方填写的 root_cause / solution

**流程**：

```
知识方：定位根因（知识创建时框架版本旧）→ 更新知识内容（标记适用版本≤x.x）→ 填写 root_cause + solution → 关闭 DTS ①（unlocated→improving→confirmed→closing）
Turing：定位根因（参数判定逻辑缺少知识触发）→ 增加知识触发点 → 填写 root_cause + solution → 关闭 DTS ②（同上）
    ↓
全部 DTS 单进入 closing → 统一触发一次回归测试
    ↓
回归输入：原 FP case 的 trace + 改进后的知识内容
Turing 重放该 case（知识方不参与重放，只负责更新知识内容）
    ↓
回归输出：重放后的 Turing 判定结果
    ↓
FP 消除判定：原始判定=FP，重放判定=TN → FP 已消除
    ↓
回归结论：回归通过 → 全部 DTS 单状态设为 passed
（若 FP 未消除 → 回归不通过 → 全部 DTS 单退回 improving，各责任方重新改进）
```

> **FN 回归判定**（仅开发态）：若 case 为 FN（漏报），回归判定逻辑为——原始判定=FN，重放判定=TP → FN 已消除 → 回归通过；重放判定=FN → FN 未消除 → 回归不通过。
