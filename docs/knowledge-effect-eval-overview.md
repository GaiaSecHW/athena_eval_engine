# 奇美拉误报归因与改进测评方案

## 0 背景：奇美拉系统现状与测评范围

### 0.1 奇美拉系统架构

奇美拉是一个 AI 驱动的漏洞挖掘系统，漏洞挖掘流程为：

> **大模型 + 漏洞挖掘 + 漏洞验证 + 知识记忆 = 漏洞**

| 组件 | 角色 |
|------|------|
| 大模型（LLM） | 推理引擎，驱动挖掘与验证的全流程 |
| 漏洞挖掘 Agent | 4 个 Agent（Turing、Argo、SecMate、DataflowVulnScan），负责入口识别→数据流追踪→漏洞模式识别→Sink 定位→判定上报 |
| 漏洞验证 Agent | 2 个 Agent（CVulnVerify、WebVulnVerify），负责漏洞理解→代码定位→验证执行→判定上报 |
| 知识记忆 | 知识库 + 记忆进化模块，为挖掘和验证提供漏洞模式、历史经验、产品文档等 |

**误报率超 30%**。从上表可以看出：知识记忆几乎贯穿所有误报类型——C7（框架自带防御 291 条）和 C3（已有校验 41 条）最典型，如果知识库里有"该框架自带输入过滤"的知识，验证 Agent 就不会误判为漏洞。但当前无法量化知识记忆到底贡献了多少误报，这正是本方案要解决的问题。

### 0.3 测评范围推导

从 §0.2 误报表可以看出：

1. **大模型**仅涉及 C6（幻觉调用链，1.1%）。幻觉问题的改进只能靠模型升级，不属于漏洞挖掘团队的可改进项。大模型涉及误报占比极低（1.1%），且无可通过测评驱动的改进路径。

2. **漏洞挖掘**占 49.2%，**漏洞验证**占 50.8%，两者合计覆盖绝大多数误报。这两个组件是 Agent 团队可改进的——改进查询策略、增加知识触发点、优化判定逻辑等。

3. **知识记忆**占 94.7%，几乎贯穿所有误报类型。知识缺失或有误是可改进的——补充知识、修正过时知识、标记适用区间。但当前无法量化知识记忆到底贡献了多少误报，这正是本方案要解决的问题。

因此，本方案分长期与短期两条路径：

| 路径 | 范围 | 改进手段 | 典型误报 | 特点 |
|------|------|---------|---------|------|
| 长期方案 | 大模型 | 跟随业界主流大模型进行升级，提升推理能力（减少幻觉） | C6 幻觉调用链（1.1%） | 效果上限高——模型升级一次，全局受益 |
| 短期方案 | 漏洞挖掘 + 漏洞验证 + 知识记忆 | Agent 改进（增加知识触发点、优化查询策略、改进判定逻辑）+ 知识记忆改进（补充缺失知识、修正有误知识、标记适用区间） | C1–C5、C7–C10（98.9%） | 可定位、可改进、可回归验证，周期短，见效快——知识补一条就少一类误报 |

**两条路径互补**：长期方案解决大模型自身的推理能力上限问题，短期方案在现有模型能力下挖掘"漏洞挖掘 + 漏洞验证 + 知识记忆"链路的改进空间。

本方案的测评范围聚焦**短期方案**——漏洞挖掘 + 漏洞验证 + 知识记忆三个组件的全链路归因，定位误报根因在这条链路的哪个环节、哪个级别，驱动针对性改进。

## 1 要解决什么问题

4 个漏洞挖掘 Agent + 2 个漏洞验证 Agent 在漏洞挖掘与验证流程中会访问知识库、记忆进化模块。误报率超 30% 时：

- 误报**根因在哪**——说不清是知识缺失、知识有误、还是 Agent 没查/查了没用
- 误报**升了还是降了**——说不清
- 是**没查到**还是**没用上**——说不清
- 是**谁的责任**——说不清
- **改了有效吗**——说不清

要拆成**八种成因（A–H）**，每种对应不同责任方和改进动作。

## 2 怎么做：五步流水线

| 步骤 | 做什么 | 具体内容 | 产出 |
|------|--------|----------|------|
| ① 数据采集 | 谁交什么 | Agent Trace、知识返回内容、知识已有内容（覆盖度/质量）、端到端结果 TP/FP/FN/TN | 原始数据集 |
| ② 知识盘点 | 先搞清楚有什么 | 覆盖度（有哪些/缺哪些）、内容质量（内容是否正确、是否有过时或误导性内容、语言/框架是否匹配） | 覆盖度清单 + 质量标注 |
| ③ 效果判定 | 按结果定效果 | 被采纳？（推理是否引用）→ 结果对？（TP/TN→正向，FP/FN→负向）→ 三种标签：正向 / 负向 / 中性 | 每次知识使用的效果标签 |
| ④ 交叉归因 | 问题出在哪 | 效果维度（正/负/中性）、生命周期维度（L0–L7 断在哪环）、业务流程维度（挖掘/验证哪个阶段）、知识来源维度（知识库/记忆进化）。一个 case 可能有多个断点，每个断点独立归因 | 交叉归因矩阵（多断点） |
| ⑤ 产出闭环 | 谁去改什么 | 指标看板（2 个核心指标）、归因报告（交叉归因矩阵）、改进建议（责任方+预期收益）、回归验证（Case 重放协议，各 Agent 自行实现重放，评测引擎判定 FP 是否消除） | 测评报告 + 改进建议清单 |

## 3 核心逻辑：误报根因全链路 L0–L7

一个误报 case 从"需不需要知识"到"知识是否影响了判定"，**L0–L7 共 8 级**。L0 标记知识的原始来源（用户上传/历史漏洞经验/已有知识升华等），不产生断链；L1–L7 逐级往下，每一步都可能断。**断在哪一步，就是哪种成因**，对应不同责任方和改进动作。

### 3.1 八级链条

| 级别 | 追问 | 断了是什么成因 | 含义 | 责任方 |
|------|------|---------------|------|--------|
| L0 | 知识来源？ | — | 知识内容的原始来源（用户上传/历史漏洞经验/已有知识升华等），仅标记 provenance，不产生断链 | — |
| L1 | 需要知识？ | — | 场景是否需要知识支撑（前置判定，不产生断链） | — |
| L2 | 发起访问？ | A 该查没查 | 需要知识但没发起访问，召回意识不足 | Agent |
| L3 | 查询准确？ | B 查询太泛/不聚焦 | 查询内容过于宽泛，没有聚焦到当前 case 的具体漏洞类型和技术栈 | Agent |
| L4 | 知识存在？ | C 查了没得 | 知识库/记忆进化里没有，覆盖度不足 | 知识方 |
| L5 | 成功取回？ | D 链路问题 | 工具失败/超时/解析错误 | Agent + 知识方 |
| L6 | 被使用？ | E 查到没用 | 召回了但推理没引用，死知识 | Agent |
| L7 | 影响结论？ | F 用了没推动 | 引用了但没改变结论，无效知识 | Agent / 知识方 |

L7 是最关键的一步，还有一条异常分支——知识推动了判定但方向错了（G），详见 3.2。

### 3.2 L7 分叉：F 与 G

| 成因 | 含义 | 责任方 |
|------|------|--------|
| **F 用了没推动** | 引用了知识但没改变结论 → 无效知识 | Agent / 知识方 |
| **G 导致误判** | 知识推动了判定，但方向错了 → 负向知识 | 知识方 |
| &nbsp;&nbsp;&nbsp;&nbsp;**└ H 内容有误** | 知识本身有问题（过时 / 不适用），是 G 的根因 | 知识方 |

**G 和 H 不是并列关系，是因果关系**：H（内容有误）是根因，G（导致误判）是 H 的结果。知识内容有误 → 知识推动了判定 → 判定方向错了 → 产生误报。

**L7 判定方法**：提取知识内容、推理引用片段、判定结论，用 LLM 做离线分析——知识正确性（对比基线漏洞信息）× 方向一致性（知识方向 vs 判定方向）→ 三种效果：正确+一致=正向，错误+一致=负向（G/H），不一致=中性（F）。LLM 无法确认时标 `l7_influenced=NULL`。

## 4 因果链：误报产生在哪个业务阶段

一个 case 跨多个业务阶段，**每个业务阶段都有独立的 L0–L7 链条**。不是在整个 case 级别做一次 L0–L7，而是每个阶段各自走一遍 L0–L7。一个误报可能在多个阶段都有断点，每个断点独立定位"哪个阶段的哪一级断了"。

### 4.1 挖掘 Agent 业务流程（5 阶段，不固定顺序）

不同挖掘 Agent 起点不同——有的从入口开始正向追踪，有的从 sink 开始逆向追踪。以下 5 个阶段都会经历，但顺序不固定：

| 阶段 | 说明 | 典型误报原因 |
|------|------|-------------|
| 入口识别 | 识别用户可控输入源 | 将不可控输入误判为可控 |
| 数据流追踪 | 追踪 source → sink 传播路径 | 路径断裂或追踪到不相关分支 |
| 漏洞模式识别 | 判断代码模式是否符合漏洞模式 | 知识误导——错误模式匹配 |
| Sink 点定位 | 定位漏洞触发的具体代码位置 | 定位到错误的 sink 点 |
| 漏洞判定与上报 | 综合判断是否为漏洞并提交 finding | 判定阈值过低 |

### 4.2 验证 Agent 业务流程（4 阶段）

| 阶段 | 说明 | 典型误报原因 |
|------|------|-------------|
| 漏洞理解 | 读取 finding 描述、理解待验证漏洞 | 误解 finding 含义 |
| 代码定位 | 定位 finding 涉及的代码位置 | 定位到错误代码位置 |
| 验证执行 | 执行分析、构造 PoC、运行测试 | PoC 构造错误 |
| 判定上报 | 写入 verdict（confirmed / ruled_out） | 将非漏洞判定为 confirmed |

### 4.3 交叉归因矩阵：业务阶段 × L2–L7

每次知识访问先标注所属业务阶段，再在该阶段内做 L0–L7 判定。一个 case 的多个阶段各自有独立的断点。以下矩阵展示每个业务阶段在各 L 级别断链时的典型成因：

**挖掘 Agent（5 阶段）**：

| 业务阶段 | L2 断（A 该查没查） | L3 断（B 查询太泛） | L4 断（C 查了没得） | L5 断（D 链路问题） | L6 断（E 查到没用） | L7 断（F 用了没推动） | L7 负向（G/H 导致误判） |
|---------|---|---|---|---|---|---|---|
| 入口识别 | 入口阶段未查知识 | 查询未聚焦入口识别方法 | 入口识别知识不存在 | 工具超时 | 召回入口知识但未引用 | 入口知识未影响判定 | 入口知识误导（误判可控输入） |
| 数据流追踪 | 数据流阶段未查知识 | 查询未聚焦数据流传播 | 数据流知识不存在 | 解析错误 | 召回数据流知识但未引用 | 数据流知识未影响路径判定 | 数据流知识误导（路径断裂） |
| 漏洞模式识别 | 模式识别阶段未查知识 | 查询未聚焦漏洞模式 | 漏洞模式知识不存在 | 工具失败 | 召回模式知识但未引用 | 模式知识未影响判定 | **模式知识误导（错误模式匹配）** |
| Sink 点定位 | Sink 定位阶段未查知识 | 查询未聚焦 sink 模式 | 该 sink 模式在知识库不存在 | 工具超时 | 召回 sink 知识但未引用 | sink 知识未影响定位 | sink 知识误导（定位错误） |
| 漏洞判定与上报 | **判定阶段未查知识** | 查询未聚焦判定标准 | 判定知识不存在 | 工具失败 | 召回判定知识但未引用 | 判定知识未影响结论 | 判定知识误导（阈值过低） |

**验证 Agent（4 阶段）**：

| 业务阶段 | L2 断（A 该查没查） | L3 断（B 查询太泛） | L4 断（C 查了没得） | L5 断（D 链路问题） | L6 断（E 查到没用） | L7 断（F 用了没推动） | L7 负向（G/H 导致误判） |
|---------|---|---|---|---|---|---|---|
| 漏洞理解 | 理解阶段未查知识 | 查询未聚焦 finding 含义 | 理解知识不存在 | 工具超时 | 召回理解知识但未引用 | 理解知识未影响理解 | 理解知识误导（误解 finding） |
| 代码定位 | 定位阶段未查知识 | 查询未聚焦代码位置 | 定位知识不存在 | 工具失败 | 召回定位知识但未引用 | 定位知识未影响定位 | 定位知识误导（定位错误代码） |
| 验证执行 | 验证阶段未查知识 | 查询未聚焦 PoC 构造 | 验证知识不存在 | 工具超时 | 召回验证知识但未引用 | 验证知识未影响 PoC | **验证知识误导（PoC 构造错误）** |
| 判定上报 | **判定阶段未查知识** | 查询未聚焦判定标准 | 判定知识不存在 | 工具失败 | 召回判定知识但未引用 | 判定知识未影响结论 | 判定知识误导（非漏洞判为 confirmed） |

→ **归因结果**：每个误报 case 可能有**多个断点**——分布在矩阵的不同格子中。每个断点独立标注成因和改进建议，一个 case 可能对应多条改进动作。

## 5 两种触发时机：开发态与运行态

同一套分析流程（L0–L7 + 因果链 + 归因），差异在于**触发时机**和**数据来源**：

| 维度 | 开发态 | 运行态 |
|------|--------|--------|
| 触发时机 | Agent 发布新版本 | 项目测试完成 |
| 基线来源 | 预置基线集（V-Bench / 漏洞中心已确认 case） | 漏洞中心人工确认结果 |
| 分析方法 | L0–L7 全链路判定（详见 §3） | L0–L7 全链路判定（详见 §3） |
| 门禁 | 不达标可阻断发布 | 误报率 > 30% 时触发预警，提醒是否进入测评分析 |

**协作闭环**：运行态发现的问题案例补入开发态基线集 → 下轮开发态验证是否改善 → 改进后发布 → 触发下一轮运行态测评。

## 6 指标体系

指标分两层：**误报 case 视角**（端到端误报率、阶段误报承担率）回答"误报有多少、分布在哪"；**知识访问视角**（负向知识率、生命周期过程指标）回答"知识在全链路中起了什么作用"。统计单元 = 每次知识访问，一个 case 可能访问多次知识，每次独立判定效果。

**只对有效 case 内的知识访问做统计**：

| 触发时机 | 有效 case 标准 |
|----------|--------------|
| 开发态 | trace 里的挖掘结论（finding 上报或中途否定）与基线漏洞/非漏洞匹配上的 case |
| 运行态 | Agent 上报了漏洞 finding 的 case |

### 6.1 端到端指标

| 指标 | 定义 |
|------|------|
| 端到端误报率（E2E FPR） | 误判非漏洞数 / (Agent命中基线漏洞数 + Agent命中基线Sink未上报数) |
| 负向知识率 | 负向效果知识访问数 / 总知识访问数 |

### 6.2 生命周期过程指标

| 指标 | 定义 | 级别 |
|------|------|------|
| M15 知识访问发起率 | 发起访问的 case 数 / 需要知识的 case 数 | L2 |
| M16 召回意识缺失率 | 未发起访问 / 需要知识的 case 数 | L2 |
| M17 查询准确率 | 准确查询数 / 总查询数 | L3 |
| M18 知识存在率 | 返回内容的查询数 / 总查询数 | L4 |

## 8 端到端案例：一个误报如何锁定根因并改进

一个 FP case 跨多个业务阶段，**每个阶段各自有独立的 L0–L7 链条**，可能存在多个断点。以下展示一个含两个断点的误报案例：

```
端到端结果：FP（误报）
    ↓
知识参与：有访问记录（计入分母）
    ↓
知识盘点：覆盖度有，但内容有误
    ↓
按业务阶段逐个做 L0–L7 判定：
    ↓
┌─ 阶段 1：漏洞模式识别
│    L1 需要？✓ → L2 发起？✓ → L3 准确？✓ → L4 存在？✓ → L5 取回？✓ → L6 引用？✓ → L7 影响？✓（推动但方向错）
│    断点：L7 → 成因 G（导致误判）/ H（内容有误为根因）
│    效果标签：负向
│    责任方：知识方
│    改进动作：更新该知识内容，标记适用区间
│    预期收益：消除该阶段的知识误导
│
├─ 阶段 2：漏洞判定与上报
│    L1 需要？✓ → L2 发起？✗（判定阶段未查询知识）
│    断点：L2 → 成因 A（该查没查）
│    效果标签：中性（未查询，无效果判定）
│    责任方：Agent
│    改进动作：增加判定阶段的知识触发点
│    预期收益：判定阶段有知识支撑，降低误判概率
    ↓
交叉归因汇总（多断点）：
    效果维度    → 负向（阶段 1 的 G/H 导致 FP）
    生命周期    → 阶段 1 断在 L7（G/H）；阶段 2 断在 L2（A）；L0 来源标记为历史漏洞经验（不产生断链）
    业务流程    → 漏洞模式识别 + 漏洞判定与上报
    知识来源    → 知识库（内容有误）
    ↓
改进建议（多条）：
    ① 知识方：更新阶段 1 引用的知识内容 → 消除知识误导
    ② Agent：在判定阶段增加知识触发点 → 补充判定依据
    ↓
回归验证：Case 重放（各 Agent 按 §7.2 协议自行实现）
    人工在 Agent 管理界面发起重放 → Agent 重放（单个 case 重头重放或中间步骤重放）→ 评测引擎从漏洞中心/Trace 读取结果 → 判定 FP 是否消除
```
